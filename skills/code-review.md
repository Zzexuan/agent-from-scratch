# 代码审查手册

## 工作流程

1. 把代码读两遍：第一遍看它**想干什么**，第二遍看它**实际会怎么跑**。这两件事经常不一致，不一致的地方就是最大的问题。
2. 按下面五项逐项检查，每项都要给出结论，**不许跳过**——只挑好挑的提，是最常见的敷衍。
3. 把问题按严重程度排序，每条给**具体改法**（能直接替换的代码），不要只说"建议优化"。
4. 最后给一句总体结论。

## 五项检查清单

### 1. 类型注解
- 函数参数和返回值有没有注解？没有注解，调用方看不出该传什么、会拿到什么。
- `def f(x)` 是缺注解；`def f(x: int) -> str` 才完整。

### 2. 异常处理
- 有没有可能抛异常却没接住的地方？重点看：文件操作、`int()`/`float()` 转换、除法、网络请求、字典取值。
- 反过来也要查：有没有 `except: pass` 这种把错误吞掉的写法？**吞掉错误比抛出来更危险**，因为调用方会拿到一个"看起来正常"的错误结果。

### 3. 边界条件
- 空输入会怎样？空列表、空字符串、`0`、`None`。
- 只有一个元素、超长输入、超大数值会怎样？
- 负数传进去会怎样？

### 4. 复杂度
- 有没有在循环里再做一层循环，或者在循环里做 O(n) 的查找（`in 列表`、`list.index`、`list.remove`）？这类写法数据量一上来就崩。
- 反复拼接字符串或列表时，该用 `append` 攒起来再 `join`，而不是一路 `+`。

### 5. 资源与副作用
- 打开的文件、数据库连接、网络连接有没有用 `with` 管起来？不用 `with` 时，一旦中间抛异常就泄漏。
- 有没有改到函数外部的东西（全局变量、传进来的可变参数）？这种副作用最难查。
- 有没有覆盖内置名字（`id`、`list`、`type`、`sum`）？

## 输出规范

严格按下面四段输出，段标题照抄：

**一、审查结论**
`通过` / `需修改` / `打回`，一句话说明理由。

**二、逐项检查**
五项各一行，格式：`- 类型注解：<问题描述>` 或 `- 类型注解：无问题`。

**三、必须修改的问题**
按严重程度从高到低编号。每条写清三件事：问题是什么 → 为什么危险 → 改法（附代码）。

**四、可选优化**
不影响正确性、但值得改的（命名、可读性、性能）。

## 注意事项

- **不要复述代码**：用户知道自己写了什么，复述等于没干活。
- 找不出问题就明说"这段没问题"，**不要为了凑数硬编**。编出来的问题会让用户改坏正确的代码。
- 代码里出现并发、加密、数据库事务时，先说"这几项不在本次检查范围"，再按五项给出能给的结论。
