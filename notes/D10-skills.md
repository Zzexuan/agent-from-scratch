## Q1：Skill 是什么？

**是什么**

给 Agent 的一段**操作说明书**——身份定位 + 工作流程 + 注意事项 + 输出规范，通常是一个按需加载的文档或文件夹。它解决的是**"怎么把领域方法论装进 Agent"**：模型知道怎么写代码，但不知道"我们团队审查代码要按哪五项查、输出要分几段"。

**我的实现（D10 里可见的证据）**

一个 `.md` 文件就是一个技能，`skills/` 目录下现在有两个：

- `skills/code-review.md`——代码审查手册：五项检查清单（类型注解 / 异常 / 边界 / 复杂度 / 资源副作用）+ 四段式输出规范
- `skills/pdf-report.md`——结构化报告手册：三段式工作流（先列大纲等人确认 → 逐节填充 → 写完自查）+ 报告骨架

协议只有三个成员（`skills/base.py:18-24` 的 `BaseSkill`）：`name`、`description`、`load_body()`。

**真实证据**（`python -m afg.demo_skills`）：

```
demo_skills.start  skills=['code-review', 'pdf-report']
skill.index        count=2 names=['code-review', 'pdf-report']
skill.load         name=code-review tokens=1017 chars=1190
tool.call          name=load_skill params={'name': 'code-review'}
```

**面试官会追问什么**

- 追问 1："Skill 和往 prompt 里塞一段说明有什么区别？" 答：**加载时机**。塞进 prompt 是"永远在场、永远占 token"；Skill 是"平时只有一行描述在场，匹配了才把全文取回来"。这就是 Q4 的渐进披露。
- 追问 2："一个项目几十个 Skill 会不会选错？" 答：会，而且 `description` 写不好是主因。判断标准和工具描述一样（D5）：**必须写清"什么场景用"和"什么场景不用"**。我这两个 skill 的 description 都显式写了"不适用：……"。

- 腾讯云《160 题》Q9（Skill 是什么）

## Q2：Skills 和 Few-shot 的区别？

**是什么**

**Few-shot 教格式，Skills 教方法论。** Few-shot 给几个"输入 → 输出"示例，让模型模仿**长什么样**；Skill 给完整的工作流程、规范、标准，教模型**怎么做事**。一个管表象，一个管过程。

**我的实现（D10 里可见的证据）**

我的 `code-review.md` 里两种都有，正好能对比：

- **方法论部分**（Skill 的本质）：五项检查清单，每项写清"怎么判"——比如复杂度那项要求"判断有没有在循环里做 O(n) 查找"。这是**过程**，没法用几个示例表达。
- **格式部分**（Few-shot 能替代）：四段式输出规范。

**真实证据**：模型输出的标题和段落顺序，和手册里写的**逐字一致**——`一、审查结论` / `二、逐项检查`（五项各一行）/ `三、必须修改的问题`（编号 + 改法代码）/ `四、可选优化`。这不是模仿了几个例子，是照着手册走的。

**面试官会追问什么**

- 追问 1："那 Skill 里还要不要放示例？" 答：要，但**示例是辅助，不是主体**。示例放在"输出规范"那一段里当锚点（"改法要给能直接替换的代码"比"改法要具体"更好懂）。主体永远是可执行的流程。
- 追问 2："Few-shot 能解决的事，用 Skill 是不是杀鸡用牛刀？" 答：是。**只调格式的场景用 Few-shot 就够了**，还省一次工具调用。Skill 的成本是多一轮 `load_skill`，只有"流程本身有价值"时才值得。

## Q3：Function Calling / Skill / MCP 三者区别？（送命题，必背）

**是什么**

三层，各管一件事：

| | 在哪一层 | 管什么 | 一句话 |
|---|---|---|---|
| **Function Calling** | 模型层 | 怎么**表达**要调工具 | 决定**说什么** |
| **MCP** | 应用层 | 工具怎么**连接**、怎么被标准化发现 | 决定**怎么连** |
| **Skill** | 知识层 | 拿到工具后**怎么做事** | 决定**怎么做对** |

**我的实现（D10 里可见的证据）**

这三层在我项目里同时存在，而且**是串联的**：

1. `load_skill` 本身是个 FC 工具（`skills/base.py:154-164` 的 `@tool`）——模型用 **FC** 的格式表达"我要加载 code-review 这份手册"
2. 手册内容取回来后由**内核**注入上下文——这一跳没有任何网络、没有协议
3. 手册里的流程指导模型怎么审查代码——**Skill** 在这里起作用

**关键观察**：`load_skill(name)` 和 D4 的 `calculator(expr)` **在代码上完全同构**——都是 `@tool` + 一行实现。**Skill 不是新机制，是"把知识当工具调"这个老机制的用法**。D11 的 MCP 才会引入真正的新东西（跨进程协议）。

**面试官会追问什么**

- 追问 1："那是不是所有知识都该做成 Skill？" 答：不是。**知识小到几百字就直接进 system prompt**（比如"回答用中文"）；大到几万字、且只有少数任务用得上，才值得做成 Skill。中间的判断线是"按需加载省下的 token 值不值得多一次工具调用"。
- 追问 2："MCP 的 resource 原语也能给模型喂文档，和 Skill 什么关系？" 答：**MCP resource 是"怎么把文档送过来"的协议，Skill 是"这份文档怎么用"的内容**。MCP 可以让远端 server 提供 skill 文件——两者是互补的，不是竞争（D11/D12 会做到）。

**参考来源**

- 知乎大厂汇总 Skills 节
- 本项目 `notes/D04-function-calling.md`、`notes/D10-skills.md` 本篇

## Q4：什么是渐进披露（progressive disclosure）？

**是什么**

上下文里**先只放索引**（name + description），模型判断需要时**再加载全文**。省 token 又不丢能力——是工具选择策略（D5 Q1）在"知识"上的应用，也是 Skills 的核心机制。

**我的实现（D10 里可见的证据）**

两跳，代码分别在两处：

- **第一跳（索引）**：`skills/base.py:121-129` 的 `inject_index()` 只拼 `- 名字：描述`，**正文一个字都不放**；`core.py:62-67` 把它拼到 system 消息后面。索引里还带一句"任务匹配某条描述时，先调 load_skill 取全文"
- **第二跳（全文）**：`skills/base.py:131-145` 的 `load_body()` 返回手册正文，由内核作为工具结果回填

**真实证据**（两段 demo，一段加载一段不加载）：

```
（审查代码）skill.index count=2 → skill.load name=code-review tokens=1017 → agent.done
（无关任务）skill.index count=2 → agent.done（iteration=1，没有 skill.load）
```

第二段跑"用一句话解释什么是上下文窗口"——模型**只看到索引就判断出都不匹配**，一次迭代直接答完，省掉了 1017 token 的手册。

**面试官会追问什么**

- 追问 1："索引本身占多少 token？" 答：索引的代价是 `技能数 × description 长度`，**随技能数线性涨**。所以技能多了之后 description 必须写短——**description 是"每次都要付的钱"**，正文是"用到才付的钱"。这个取舍决定了 description 该写多详细。
- 追问 2："手册太长撑爆上下文怎么办？" 答：我在 `skills/base.py:137-144` 的处理是**打告警，不静默截断**——手册被切掉一半比多花点 token 更危险（模型会照着半截手册干出奇怪的事）。真要控制长度，应该在**写手册时**控制，而不是运行时偷切。
- 追问 3："渐进披露能不能做三层？" 答：能。真实系统（包括你每天用的编程助手）常见是"索引 → 摘要 → 全文"三层。**每多一层就多一次往返**，只有文档量真的很大时才值得。

**参考来源**

- 博客园《Skills vs Subagents 本质区别》

## Q5：Skills vs Subagents 本质区别？

**是什么**

- **Skill = 给同一个 Agent 加"操作说明"**：不隔离上下文、没有独立执行、就是往当前上下文里注入一段文本
- **Subagent = 独立上下文的自治 Worker**：自己的上下文窗口、可并行、干完只回结论

一句话：**一个是"读手册"，一个是"派专人"**。

**我的实现（D10 里可见的证据）**

`load_skill` 的行为可以逐条对照：

- 它返回一个**字符串**（`skills/base.py:155-164`），内核按普通工具结果 append 进 messages——**没有任何新进程、新上下文**
- 主 Agent 的 `messages` 列表**原封不动地继续用**，只是多了几段文本
- 加载完的手册**一直在上下文里**，直到被压缩器（D3）压掉或对话结束

**这条对比为什么重要**：D15 要写的 `SubAgentTool` 长的样子**和 `load_skill` 几乎一样**（都是 `@tool` + 一行调用），但内部会起一个**带独立 messages 的新 AgentCore**、干完只把最终结论返回。**接口一样、语义完全不同**——这正是面试爱问的点。

**面试官会追问什么**

- 追问 1："什么时候该用哪个？" 答：**看上下文要不要隔离**。任务需要读 10 万字材料但只回 3 行结论 → 用 Subagent（否则那 10 万字全进主上下文）；任务是一套要复用好几轮的做事规范 → 用 Skill（规范得留在主上下文里才能持续指导）。
- 追问 2："Skill 会不会把主上下文搞脏？" 答：**会**，而且这是它在长任务里的主要缺点。手册一旦加载就占着位置；缓解办法是任务切换时主动丢弃（把那段消息从 messages 里摘掉）——今天没做，是明确的缺口。
- 追问 3："Subagent 能加载 Skill 吗？" 答：能，而且很常见——**子代理自己挂一个 SkillLoader**，父代理只管派活。两条线是正交的。

**参考来源**

- 博客园《Skills vs Subagents 本质区别》

## Q6：为什么用 Skill 文件而不是把所有规范塞进 system prompt？

**是什么**

三个理由：**token 预算**（全塞会占满窗口，且大部分场景用不上）、**按需加载**（渐进披露）、**可独立版本管理 + 跨项目复用**（文件能进 git、能被别的项目引用，prompt 里的字符串不能）。

**我的实现（D10 里可见的证据）**

算一笔账就清楚了：

- 两份手册合计约 **2000 token**（code-review 单份就是 1017）
- 如果常驻 system prompt，**每一次对话**都要付这 2000 token
- 现在的索引：`skill.index count=2` —— 索引只有两行，**几十个 token**
- demo 第二段跑无关任务时，白省了 1017 token（日志里没有 `skill.load`）

而且技能是**独立文件**：用 git 管理，改动有 diff、有历史；别的项目直接拷 `skills/` 目录就能复用。

**面试官会追问什么**

- 追问 1："那 system prompt 里还剩什么？" 答：**永远成立的东西**——身份（"你是乐于助人的助手"）、输出语言、安全边界。判断标准：**"这段话在 99% 的对话里都用得上吗"**，是就常驻，不是就做成 Skill。
- 追问 2："技能和主指令冲突了怎么办？" 答：**主指令优先**。我的索引文字里写的是"任务匹配某条描述时先调 load_skill"——它是**建议性**的，没有覆盖 system prompt 里已有的规则。真出现冲突要在手册里写清楚边界，而不是指望模型自己权衡。

## Q7：一个 Skill 文件的标准结构？

**是什么**

**YAML frontmatter**（`name` + `description`，`description` 决定它何时被选中）+ **正文**（工作流程步骤 / 规范 / 示例 / 边界与禁忌）。`description` 要写**具体场景**，"用于通用任务"等于没写。

**我的实现（D10 里可见的证据）**

解析在 `skills/base.py:42-83`，手写的，没引 yaml：

- `split_frontmatter`（`:42-55`）：首行必须是 `---`，往后找到下一个 `---` 收尾；前面是头部，后面是正文
- `parse_fields`（`:58-69`）：逐行按 **第一个**冒号切（`:65` 的 `split(":", 1)`）——因为 description 里可能出现 ASCII 冒号（网址、时间）
- `read_skill_file`（`:72-83`）：`:78-82` 两道必填校验，**`name` 或 `description` 缺一个就直接报错**

**"description 必填"是硬规则**：它是渐进披露唯一的入口（Q4）。空 description 的技能**永远不会被加载**——让它静默存在比直接报错更坏，所以我在扫描阶段就拦下来。

**description 的写法**，我这两个技能都按同一个模板：

```
触发场景：用户贴出一段代码问"有没有问题"……
不适用：从零写新代码、解释代码是什么意思、排查已经报错的堆栈。
```

**"不适用"那一句和"触发场景"一样重要**——只写"什么时候用"，模型会把技能往所有沾边的任务上套。

**面试官会追问什么**

- 追问 1："为什么不用 pyyaml 解析？" 答：**frontmatter 只有两个简单字段**，手写 30 行能搞定，而且报错信息能写成"第 1 行必须是 ---"这种人话。引一个依赖换来的通用性用不上，还多一个出错面。**等字段复杂到支持嵌套和列表时再换**。
- 追问 2："技能文件能不能带脚本/资源？" 答：能，真实系统里 skill 常常是**一个目录**（SKILL.md + 模板 + 脚本）。今天只做了单文件版本——`BaseSkill` 协议里的 `load_body()` 只返回文本，要支持资源得再加方法（**接口留了余地，实现没跟上**）。

## Q8：Skill 加载进来的内容放上下文哪个位置？

**是什么**

作为 **system 或 user 消息段**注入，并**明确标注边界**（如 `<skill name="...">`）；任务结束可以丢弃；要避免与主指令冲突。

**我的实现（D10 里可见的证据）**

我的做法是**分开放的**：

- **索引** → 拼进 **system 消息**（`core.py:62-67`）。理由：它是"系统级能力清单"，位置和 system prompt 一致，模型不容易忽略
- **手册全文** → 作为**工具结果**回填（`role=tool`）。理由：走的是 D4 的 FC 标准回路，`tool_call_id` 一一对应，**不需要发明新的消息类型**

**边界标注**：索引那一行开头就写了"你可以加载以下技能手册"，加载完的正文本身有 `# 代码审查手册` 这样的标题——**靠内容自身的结构标边界**，没加 XML 标签。

**诚实的缺口**：任务结束**没有主动丢弃**手册（Q5 追问 2 提过）。今天靠 D3 的压缩器兜底——上下文超阈值时它会把旧内容压掉。**主动丢弃是明确的待办**，不是"设计成这样的"。

**面试官会追问什么**

- 追问 1："为什么不给注入的正文加 `<skill>` 标签？" 答：**信息少时不加**——标签是防混淆用的，而我的手册有清晰标题、且是独立一条消息，混淆风险低。当上下文里同时存在多个来源的同类文档时（比如手册 + 检索结果 + 用户输入都是长文本），标签就变成必需的了。
- 追问 2："手册放 system 和放 tool 结果，模型的行为有区别吗？" 答：**有**。system 里的内容模型当成"长期规则"，tool 结果模型当成"这一次查到的信息"。手册是**做事的方法**，更像规则，严格说放 system 更贴切；我选 tool 结果是为了复用现成的 FC 回路。这是**工程便利压过语义精确**的一处妥协。
