## Q1：上下文工程四策略是什么？（必背框架）

**是什么**

把 LLM 比作 CPU、上下文窗口比作 RAM，那么"上下文工程"就是**内存管理**。四策略：

| 策略 | 一句话 | 典型手段 |
|---|---|---|
| **Write**（写出去） | 关键信息持久化到窗口之外，需要时再读回 | Scratchpad、NOTES.md、记忆库 |
| **Select**（按需取） | 不把全部信息塞进去，用到哪块检索哪块 | RAG、记忆检索、工具按需加载 |
| **Compress**（压一压） | 旧内容换摘要或裁剪 | auto-compact、工具结果裁剪、中间截断 |
| **Isolate**（隔出去） | 大量信息在别处处理，主上下文只收结论 | 子代理、沙盒、运行时状态对象 |

**我的实现（D3 里可见的证据）**

D3 只做了四策略里的 **Compress** 这一块（Write/Select/Isolate 分别是 D8 记忆、D9 RAG、W3 子代理的任务）：

`src/afg/context/compressor.py:23` `compress()` 就是 Compress 的最小实现：
```python
primers = messages[:PRIMER_COUNT]      # 开头几条原样留
summary_message = ...                  # 中间段压成一条摘要
recent = messages[len(messages) - recent_count :]   # 最近几条原样留
result = primers + [summary_message] + recent
```

**面试官会追问什么**

- 追问 1："四策略里哪个优先级最高？" 答：没有绝对优先级，看信息价值/替换代价。**Write 最先做**——能在信息产生时就落盘，后面就不需要压；**Compress 是兜底**，只在窗口快满时才跑，因为压缩有损且要额外调一次 LLM。
- 追问 2："你这四策略只做了 Compress，算懂上下文工程了吗？" 答：知道四策略是框架层，实现是一天一块的。D3 的压缩器是"兜底策略"，D8/D9 补上 Write/Select 后，压缩被触发的频率会明显下降——**这才是四策略一起用的意义**。

- LangChain《Context Engineering for Agents》（四策略原始出处）
- Anthropic《Effective context engineering for AI agents》: https://www.anthropic.com/research/effective-context-engineering-for-ai-agents

## Q2：Prompt Engineering 和 Context Engineering 的边界？

**是什么**

两句话分清：

- **Prompt Engineering** 管"**怎么说**"——单轮输出控制：角色设定、输出格式、约束条件、few-shot 示例。
- **Context Engineering** 管"**基于什么说**"——多轮状态治理：什么信息进入窗口、保留多久、什么时候淘汰、需要时怎么取回。

类比：PE 是"这一句话怎么措辞"，CE 是"这个人脑子里此刻装着哪些信息"。

**我的实现（D3 里可见的证据）**

D3 这一天的代码里两者同时存在，边界很清楚：

- **PE 的部分**：`compressor.py:3` 的 `SUMMARY_SYSTEM_PROMPT` —— 它就是在教模型"怎么说话"："只保留任务目标/关键决策/重要发现/未解决问题/犯过的错误，丢弃过程性描述，直接输出摘要正文"。这是**提示词工程**：写错它就压得不好。
- **CE 的部分**：`chat.py:66` 那一整段的判断与重建 —— 什么时候压、保留前 3 条、保留后 N 条、压到多少。这是**状态治理**，跟模型说什么无关。

**面试官会追问什么**

- 追问 1："PE 还重要吗？都说 CE 更重要。" 答：都重要，但**杠杆不同**。PE 的收益上限是"单轮回答质量"，CE 的收益上限是"任务能跑多长"。Agent 项目里 PE 决定单个环节好不好，CE 决定整个任务跑不跑得完。
- 追问 2："能举例说明两者会互相影响吗？" 答：能。我的压缩器 prompt 写得越"惜字如金"，压完剩下的 token 越少，能塞进的历史就越长——**PE 的质量直接决定了 CE 的效果上限**。反过来，CE 压得太狠，模型的 prompt 再好在信息缺失下也无能为力。

**参考来源**
- LangChain 博客（PE vs CE 边界节）
- Anthropic《Effective context engineering for AI agents》

## Q3：Claude Code 的 auto-compact 是怎么做的？

**是什么**

三个关键数字/做法：

1. **触发**：上下文用量超过约 95% 时触发（Claude Code 实测阈值偏高，因为它窗口大）。
2. **动作**：把整段交互轨迹**总结成一段摘要**，然后用摘要**重开一个新窗口**继续。
3. **最简形态**：如果不想做 LLM 摘要，最简单的压缩就是**清掉历史里原始的工具调用结果**——因为工具返回往往是整个上下文里最占 token 的部分，而且大多数用完就不需要了。

**我的实现（D3 里可见的证据）**

我的压缩器是"低配版 auto-compact"：同样是把旧轨迹换摘要，但我**不重开窗口**，而是原地替换（保留会话身份、`trace_id` 不变）。

`src/afg/context/compressor.py:37-56`：
```python
while True:
    middle = messages[PRIMER_COUNT : len(messages) - recent_count]
    summary_text = self._summarize(middle, llm)
    summary_message = Message(role="system", content=SUMMARY_PREFIX + summary_text)
    recent = messages[len(messages) - recent_count :]
    result = primers + [summary_message] + recent
    if counter.count_messages(result) <= self.budget * self.target_ratio:
        return result
    recent_count = recent_count // 2
```

与 Claude Code 的三个差异，正好是我能答的对比点：
- **触发阈值不同**：我用 75%（`window.py:3` 的 `COMPRESS_THRESHOLD`），Claude Code 用约 95%。我留 25% 余量更保守。
- **不重开会话**：我在同一个 `messages` 列表上原地重建，`trace_id` 不变——**压缩不改变会话身份**。
- **没做工具结果专项裁剪**：这是 Q6 里五级降级的第一级，我留到接入工具之后的 D6+ 再做。

**面试官会追问什么**

- 追问 1："为什么 Claude Code 敢用 95%，你用 75%？" 答：跟窗口大小和**单轮增量**有关。窗口 20 万时 5% 余量有 1 万 token，够一轮输入输出；我这里的实验窗口调到了 8192（`config.py` 的 `context_window_tokens`），5% 只有 400 token，一轮就撑爆。**阈值应该按"单轮最大增量 / 窗口"来定，不是拍脑袋。**
- 追问 2："为什么不干脆重开会话？" 答：重开更干净（避免残留的坏摘要影响后续），但会丢失"我正在做的这件事"的连续性，且用户视角会看到会话被切断。原地替换的代价是要自己保证摘要质量和结构正确。

**参考来源**
- 博客园《拆解 Claude Code SubAgent》
- Anthropic《Effective context engineering for AI agents》

## Q4：三段式保留策略是什么？

**是什么**

压缩后保留三段，各有用处：

| 段 | 保留什么 | 为什么不能丢 |
|---|---|---|
| **Primers** | 开头 3 条左右 | 最初的任务设定、system 人设。丢了模型就不知道自己在干什么 |
| **Summary** | 中间段压成的 1 条摘要 | 保留关键决策/发现/未解决问题。丢了就"失忆" |
| **Recents** | 最近 N 条原样 | 维持连贯性。用户问"刚才那个方案"，得找得到 |

**为什么不是"只留最近几条"**：那样模型会丢掉最初的系统指令和任务目标，表现为"聊着聊着开始胡说"。

**我的实现（D3 里可见的证据）**

`src/afg/context/compressor.py:12` `PRIMER_COUNT = 3`，`compressor.py:24` 取前 3 条，`compressor.py:45` 造摘要消息，`compressor.py:47` 取最近段，`compressor.py:48` 拼起来。测试 `tests/test_compressor.py::test_compress_three_part_structure` 把结构钉死：
```python
assert len(result) == 3 + 1 + 3
assert result[0:3] == messages[0:3]        # 前 3 条原样
assert result[4:7] == messages[7:10]       # 后 3 条原样
```

摘要消息的格式在 `tests/test_compressor.py::test_summary_message_format_and_position` 里断言：
```python
assert summary.role == "system"
assert summary.content.startswith("[历史摘要] ")
```

**面试官会追问什么**

- 追问 1："Primers 为什么是 3 条？" 答：经验值，够放下 system 人设 + 最初的任务描述。硬编码成常量（`PRIMER_COUNT = 3`）是为了以后能按实测调，不是拍脑袋写死。**更好的做法是按内容判断**（哪些是 system、哪些是最初任务），但 v1 先简单。
- 追问 2："摘要用 role=system 插在中间有问题吗？" 答：**有问题，这是我知道的一个不规范点**。协议惯例 system 只放最前，放中间多数网关能接受但不标准。我选它是为了对齐 D3 规格；退路是改 `role="user"` 并保留 `[历史摘要]` 前缀（前缀才是真正的机器标记，role 只影响模型怎么理解这段话）。

**参考来源**
- 主文档《核心接口规格》上下文管理节
- waylandz《AI Agent 开发实战》第 7 章压缩节

## Q5：什么时候触发压缩？为什么不是每次都压？

**是什么**

- **触发点**：预算使用率约 **75%**。
- **目标**：压到约 **37.5%**（正好一半）。
- **为什么是 75% 不是 100%**：1.0 的时候连"这一轮要发的消息 + 要输出的答案"都塞不下了。留 25% 给当前轮的输入输出。
- **为什么每次不压**：摘要要**额外调一次 LLM**（几百毫秒到几秒，还花钱），而且压缩**有损**。每次都压 = 又慢又贵又丢信息。

**我的实现（D3 里可见的证据）**

两个文件分工明确，这层分工是 D3 的关键设计：

- **`window.py` 管"该不该压"**：`window.py:30` 的 `should_compress=usage >= COMPRESS_THRESHOLD`，阈值 `window.py:3` = 0.75。
- **`compressor.py` 管"怎么压"**：它自己不判断该不该压，被调用才压。

`chat.py:66` 是两者的接缝：
```python
if report.should_compress:
    messages = compressor.compress(messages, llm, counter, ctx_cfg.compress_keep_recent)
```

37.5% 这个目标在 `compressor.py:50` 被**真实执行**，不是写个注释就算：
```python
if counter.count_messages(result) <= self.budget * self.target_ratio:
    return result
```

**面试官会追问什么**

- 追问 1："一次压不到目标怎么办？" 答：我在 `compressor.py:52-56` 做了减半重试——`recent_count //= 2`，下限 4 条，每次重试**重新生成摘要**（因为丢掉的 Recents 会并进中间段，不重生成就永久丢失）。代价是重试会多花一次 API 调用，所以我把下限设得比较低、让循环最多跑两三次。
- 追问 2："如果压完还是超阈值呢？" 答：`chat.py:82` 会打一条 `context.still_full` 警告。这表示"压缩也没救了"——通常是最近的消息本身就太大，该走 Q6 的五级降级（比如裁工具返回），或者提示用户开新会话。

**参考来源**
- Claude Code / Shannon 的实践（75% 触发、压到一半）
- 腾讯云《Agent 里怎么系统性管理上下文？溢出怎么办？》

## Q6：窗口溢出时的五级降级顺序？

**是什么**

按"信息价值 / 替换代价"从低到高排，尽量先动代价小的：

| 级别 | 动作 | 说明 |
|---|---|---|
| ① | **裁工具返回** | 非关键字段砍掉。工具返回最占 token，性价比最高 |
| ② | **压缩对话历史** | 旧消息换摘要，留最近 3 轮完整 |
| ③ | **减少 RAG 文档** | Top-5 降到 Top-2 |
| ④ | **简化系统指令** | 把冗长的 system prompt 砍短 |
| ⑤ | **终止任务** | 提示用户开新会话 |

核心排序逻辑：**越"原始、越可重新获取"的信息越先丢；越"不可复现、越关系目标"的信息越后丢。**

**我的实现（D3 里可见的证据）**

D3 只实现了第 ② 级（压缩对话历史）。原因：① 需要先有工具（D4-D6），③ 需要先有 RAG（D9）。

所以严格说，我现在的压缩器在降级链里是**孤零零的一级**——它的下游（④⑤）和上游（①）都还没建。这一点在 `chat.py:82` 体现得很清楚：
```python
if after_report.should_compress:
    logger.warning("context.still_full", ...)
```
压完还超，现在只能打警告，因为**下一级（简化系统指令）还没实现**。

**面试官会追问什么**

- 追问 1："为什么不直接从第①级开始？" 答：因为①的效果最好但**依赖工具系统存在**。有了工具之后（D4 起），我会把"工具结果裁剪"做进压缩器前面——先裁再压，能显著降低压缩频率。**这也是 D3 先做②的合理性：它在任何场景都适用，不依赖别的模块。**
- 追问 2："第⑤级'终止任务'会不会太粗暴？" 答：它是最后的安全阀。比"硬发一个超长请求被 API 拒掉"要好——至少用户知道发生了什么、可以开新会话继续。工程上宁可明确失败，不可静默出错。

- 腾讯云《一文读懂大模型长文本处理》（降级节）

## Q7：中间截断法（middle truncation）是什么？什么时候用？

**是什么**

对**超长的单条文档**，砍掉中间、保留头尾：
- 保留**开头**：文档开头常有摘要、目录、结论预告
- 保留**结尾**：结尾常有总结
- 砍**中间**：中间的论证过程最可牺牲

**为什么不适用于对话历史**：对话的价值集中在**最近几轮**（Recents），不在开头；中间截断会把最近的内容砍掉，等于把用户刚说的话丢了。所以对话历史要用"三段式"（Q4），单文档预处理才用中间截断。

这个现象有理论依据：**Liu et al.《Lost in the Middle》** 发现模型对上下文**开头和结尾的信息利用得最好，中间的信息容易被忽略**——中间截断正是利用了这个特性。

**我的实现（D3 里可见的证据）**

D3 的压缩器**没有**做中间截断，但它的三段式结构恰好和"Lost in the Middle"的结论对齐：

`compressor.py:24` / `compressor.py:47`：
```python
primers = messages[:PRIMER_COUNT]                     # 保开头
recent = messages[len(messages) - recent_count :]     # 保结尾
```
**中间段正是被压掉的部分**——这就是为什么三段式在结构上等价于"对对话历史做保头尾的截断"，只不过中间不是直接丢弃而是换成了摘要。

**面试官会追问什么**

- 追问 1："既然模型中间信息利用差，那把重要信息放中间是不是就白放了？" 答：**这是真实风险**。所以我的 `SUMMARY_PREFIX = "[历史摘要] "` 前缀不只是标记，也是给模型的强提示；更好的是把摘要放在开头（primers 之后立刻放），我目前就是放在第 4 位（紧跟 3 条 primers），比放中间靠前。
- 追问 2："工具返回太长时，你用中间截断还是直接截尾？" 答：会**先试中间截断**——工具输出（比如 JSON、日志）常常开头有结构、结尾有结论。这属于 Q6 的第①级，等 D4-D6 有工具之后再实现。

**参考来源**
- Liu et al.《Lost in the Middle: How Language Models Use Long Contexts》: https://arxiv.org/abs/2307.03172
- 腾讯云《一文读懂大模型长文本处理》

## Q8：压缩是有损的，保留什么丢弃什么？

**是什么**

**保留**（信息价值高、不可复现）：
- 任务目标
- 关键决策（做过什么选择、为什么）
- 重要发现
- 未解决的问题
- **错误尝试**——错误是学习信号

**丢弃**（可复现、价值低）：
- 原始工具输出（需要时能重跑）
- 中间啰嗦的推理过程
- 重复内容

**特别注意的反模式**：把"错误的上下文"清掉。看起来是"清理"，实际上是**让 Agent 把已经踩过的坑再踩一遍**——因为模型失去了"这条路走不通"的记忆。

**我的实现（D3 里可见的证据）**

这些取舍**逐条写进了压缩器的提示词**，`src/afg/context/compressor.py:3-8`：
```python
SUMMARY_SYSTEM_PROMPT = (
    "你是一个对话历史压缩器。把下面这段对话压缩成一段简短摘要，遵守三条规则：\n"
    "1. 保留：任务目标、关键决策、重要发现、还没解决的问题、犯过的错误。\n"
    "2. 丢弃：过程性描述、寒暄、重复内容、完整的原始输出。\n"
    "3. 直接输出摘要正文，不要加任何开头语或解释。"
)
```
注意第 1 条里的"**犯过的错误**"——这就是刻意对抗上面那个反模式。

`temperature=0.3`（`compressor.py:71`）也是刻意的：摘要要**稳定**，同一段历史每次压出来应该差不多，不能发散。

**面试官会追问什么**

- 追问 1："怎么验证摘要真的保住了这些？" 答：这是 D20 评测日的任务（trajectory 级别的评测）。D3 目前只能靠人工看，但我留了抓手——`context.compress` 日志里有压缩前后的 token，压缩率异常（比如接近 1.0 或超过 1.0）说明摘要没起到作用。
- 追问 2："压缩率多少算健康？" 答：**要看中间段有多大**。中间段 1 条消息时，摘要可能比原文还长，压缩率会 > 1.0（我的小窗口联调就实测到了 `ratio=1.105`）——**这时压缩是负收益**。中间段几十条时压缩率能到 0.5 甚至更低。所以压缩率不是固定指标，要看"压了多少条消息"，不能只看比值。

**参考来源**
- waylandz《AI Agent 开发实战》第 7 章
- Anthropic 多智能体研究（错误保留的必要性）

## Q9：写上下文（Write）的 Scratchpad 是什么？

**是什么**

把关键信息**持久化到上下文窗口之外**（文件 / 状态对象字段），需要时再读回来。

最典型的例子：Anthropic 的多智能体研究里，lead researcher **先把 plan 写进 memory**，再去派发子任务——这样即使自己的窗口被截断，plan 也不会丢。

**Write 和 Compress 的关系**：Write 是**治本**，Compress 是**治标**。信息在产生的那一刻就落盘，后面根本不需要靠压缩去抢救。所以四策略里 Write 的优先级最高。

**我的实现（D3 里可见的证据）**

D3 **没有实现** Write（Scratchpad 属于 D8 记忆模块的任务）。但 D3 的代码里有一个**雏形**：

`chat.py` 里的 `messages` 列表本身就是"窗口内的 Write"——把每条 user/assistant 消息都 append 进去，就是最朴素的"写下来"。真正的 Scratchpad 是把它挪到窗口外（文件/数据库）。

另一个更接近 Scratchpad 的现有物是 **`chat.log`**：单条日志就是一行 JSON（`observability/logging.py`），里面带着 `trace_id` 和 `step`。它满足 Scratchpad 的两个特征：**在窗口之外**、**可检索**。D8 的 `SQLiteMemory` 会把它升级成"能被 LLM 按需读回"的形式。

**面试官会追问什么**

- 追问 1："Scratchpad 和 RAG 的区别？" 答：都是"信息在窗口外"。区别在**写入方**：Scratchpad 是 **Agent 自己主动写**的（我知道这个重要，先记下来）；RAG 的知识库是**外部预先存在**的（我去检索别人的资料）。所以 Scratchpad 属于 Write 策略，RAG 属于 Select 策略。
- 追问 2："为什么不干脆把整个对话都存文件里，需要时全读回来？" 答：读回来也要占窗口。Scratchpad 的价值在**筛选**——写的时候就已经提炼过一轮，读回来的是高密度信息。全量存储 + 全量读回等于没压缩。

## Q10：隔离（Isolate）有哪些手段？

**是什么**

三种手段，都是"让大量信息在别处处理，主上下文只收结论"：

| 手段 | 怎么隔离 | 主上下文收到什么 |
|---|---|---|
| **多代理** | 子代理开**独立窗口** | 只收子代理的最终结论 |
| **沙盒** | 代码在沙盒里执行 | 只收返回值（不把执行过程的大输出带回来） |
| **运行时状态对象** | 状态存在结构化对象里 | 按字段**选择性注入**，不是整个对象塞进去 |

这是四策略里"最省 token"的一种——因为信息**根本没进过主窗口**，不是"进来再压"。

**我的实现（D3 里可见的证据）**

D3 完全没做 Isolate（那是 W3 的 D15-D18）。但 D3 的代码里已经能看到"**为什么需要它**"的证据：

1. **`ContextReport`（`window.py:6`）= 运行时状态对象的雏形**。`window.check()` 数完 token 后不是把整个 `messages` 传回来，而是只回一张报告单：
```python
class ContextReport(BaseModel):
    total_tokens: int = 0
    budget: int = 0
    usage_ratio: float = Field(default=0.0, ge=0.0)
    should_compress: bool = False
```
**这就是"字段级选择性注入"**——下游（`chat.py`）只看到 4 个数字，看不到原始消息。

2. **压缩器的返回值也是隔离**：48 条消息进去，出来的是"3 条 + 1 条摘要 + N 条"，**中间那 30 多条根本没有出现在后续任何一轮的上下文里**。

3. **`llm.chat()` 的接口本身就是隔离设计**：`deepseek_client.py:52` 返回的 `LLMResponse` 只装 `content` / `tool_calls` / `usage` 三样，**API 返回的原始 JSON（几十个字段）被隔离在 `deepseek_client.py` 内部，从没进过 chat.py 的上下文**。

**面试官会追问什么**

- 追问 1："子代理隔离最容易被忽略的好处是什么？" 答：**省的不只是 token，还有"污染"**。子代理探索失败的几十步过程如果进主上下文，不仅占 token，还会让主 Agent 的推理被无关细节带偏。**隔离同时解决了"容量"和"信噪比"两个问题**。
- 追问 2："沙盒隔离和普通 subprocess 有什么区别？" 答：沙盒的重点不在"隔离上下文"，而在**安全**（超时/黑名单/输出截断，见 D13）。但顺带也做了上下文隔离——命令输出 10000 行，进上下文的只有被截断的 4000 字符。
- 追问 3（D3 与 W3 的衔接）："你这三天的压缩器，接了子代理之后还有用吗？" 答：**更有用，但触发频率会降**。子代理让大量信息不进主窗口，主窗口膨胀变慢；但主窗口自己仍会随着"派发-收结论"的轮次增长，兜底压缩依然必要。**四策略不是替代关系，是分层防御。**

## 今日真实体验记录（30 轮真实对话实验）

**实验设置**：模型 `deepseek/deepseek-v4.1-flash`（ZCode 的 commandcode 通道），窗口 8192、预算 6144、触发阈值 75%（= 4608 token）、`compress_keep_recent=20`、目标 37.5%。
**做法**：喂 30 个不同话题，每个都要求"用 3-4 句话解释"，逼出长回复（信息型对话）。

**每轮 token 增长**

| 轮次 | 总 token | 使用率 | 轮次 | 总 token | 使用率 |
|---|---|---|---|---|---|
| 1 | 241 | 3.9% | 17 | 3565 | 58.0% |
| 2 | 445 | 7.2% | 18 | 3757 | 61.1% |
| 3 | 686 | 11.2% | 19 | 3943 | 64.2% |
| 4 | 875 | 14.2% | 20 | 4223 | 68.7% |
| 5 | 1044 | 17.0% | 21 | 4442 | 72.3% |
| 6 | 1257 | 20.5% | **22** | **4728** | **77.0%** ← 触发压缩 |
| 7 | 1476 | 24.0% | **23** | **1869** | **30.4%** ← 压缩后 |
| 8 | 1730 | 28.2% | 24 | 2128 | 34.6% |
| 9 | 1957 | 31.9% | 25 | 2312 | 37.6% |
| 10 | 2165 | 35.2% | 26 | 2558 | 41.6% |
| 11 | 2353 | 38.3% | 27 | 2796 | 45.5% |
| 12 | 2536 | 41.3% | 28 | 3065 | 49.9% |
| 13 | 2759 | 44.9% | 29 | 3302 | 53.7% |
| 14 | 2956 | 48.1% | 30 | 3497 | 56.9% |
| 15 | 3143 | 51.2% | | | |
| 16 | 3372 | 54.9% | | | |

**压缩事件（只发生 1 次）**

```json
{"event": "context.compress", "step": 22,
 "messages_before": 45, "messages_after": 14,
 "before_tokens": 4728, "after_tokens": 1648,
 "ratio": 0.349, "compress_ms": 6223.9}
```

**五条结论（写进笔记的取舍）**

1. **触发点精确命中设计值**：第 22 轮末 4728 token = 77.0%，刚越过 4608 阈值。平均每轮 **+214 token**，从 241 起到 4728 用了 21 轮——和你 D02 笔记实测的长回复斜率（+145/轮）同量级，偏高是因为这次回复更长（3-4 句技术解释）。

2. **压缩效果超过目标**：45 条 → 14 条，4728 → 1648 token，**压缩率 0.349**，优于 37.5% 的目标。

3. **减半重试真的生效了**：14 = 3 条 Primers + 1 条摘要 + **10 条** Recents。`keep_recent` 初始是 20，结果只保留了 10 —— 说明第一次拼装（24 条）没达标，循环执行了 `recent_count = 20 // 2 = 10` 才通过。耗时 6.2 秒（两次摘要调用）正是这个的证据，**不是代码在偷懒**。

4. **压缩不改增长规律，只把起点拉低**：第 23 轮从 1869 重新爬，斜率还是每轮 +184~+269。所以压缩**不解决膨胀，只是续命**——按这个斜率，第二次压缩大约在第 23 + (4608-1869)/214 ≈ 36 轮，也就是**每 13-15 轮压一次**。这个"压缩间隔"才是衡量压缩器好坏的真正指标。

5. **压缩率不是固定指标，要看"压了多少条消息"**：这次的 0.349 是因为中间段有 32 条消息，摘要（几百 token）替换掉了几千 token，非常划算。而我在小窗口联调（窗口 700）时实测到 **`ratio=1.105`** —— 中间段只有 1 条消息时，摘要比原文还长，**压缩是负收益**。所以单看压缩率会误判，得结合中间段大小一起看。

**真实踩坑**

1. **压缩空转 bug（小窗口联调抓到的）**：原来的切分写成 `recent_count = min(keep_recent, available)`。当消息条数少（`available < keep_recent`）时，"最近段"会把**所有**消息都吃掉，中间段变成空的，压缩直接原样返回——日志表现为 `messages_before=5 messages_after=5 ratio=1.0 compress_ms=0.0`（连 LLM 都没调），同时不断打 `context.still_full` 警告。
   **修法**：`recent_count = min(keep_recent, available - 1)`，保证至少留 1 条给中间段。这行顺带保证了一件更重要的事——**最后一条（用户当前这轮）永远不会被压进摘要**。
   **防线**：加了回归测试 `test_never_summarizes_the_last_message`，改回去就会红。

2. **小窗口联调暴露的第二个现象**：窗口调到 700 时，第 2 轮 `ratio=1.105`，上下文不降反升。原因见结论 5。这不是 bug 而是**压缩的本质限制**：中间段太小时不值得压。真实场景（中间段几十条）不会遇到。

3. **阈值 75% 是"预警线"不是"安全线"**：这轮实验第 22 轮 77.0%，已经超过阈值才触发压缩；压缩期间上下文其实已经略微超出设计区间了。这印证了 D02 笔记的判断——**反应式压缩天生滞后**，真正的解法是 Write（提前落盘）而不是压得更勤。

**成本**：实验本体 30 次对话调用 + 2 次摘要调用 = **32 次真实调用**，总耗时 101.7 秒。
