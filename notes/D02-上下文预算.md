## Q1：Agent 的上下文里到底装了什么？

**是什么**
四类内容：
1. **指令**：system prompt、工具描述、few-shot 示例——一次性写入，基本静态。
2. **知识**：检索回来的文档（RAG 内容）——按需注入，多轮可增。
3. **记忆**：历史对话（user/assistant 往返）——每轮必增。
4. **工具结果**：每次 Observation（工具返回、文件内容、报错）——动态注入。

Agent 与 Chatbot 的区别就在**后两类会持续膨胀**：Chatbot 的历史只增不删尚且可控，Agent 每步工具返回动辄几百上千 token，膨胀速度快一个量级。

**我的实现**
`chat.py` 的 `messages` 列表就是这四个份额的物理载体（目前只有指令+记忆两席，D4 起工具结果进场占第三席）：
```python
messages: list[Message] = [Message(role="system", content=SYSTEM_PROMPT)]  # ①指令
# 循环里 append user（②记忆）+ assistant（②记忆）+ 未来 tool 结果（④工具结果）
```
`ContextWindow.from_model(窗口, 安全系数)` 把"四份额的配额"抽象成单一 budget。

**面试官会追问什么**
- 追问："四类里哪类最占地方？" 答：工具结果与 RAG 知识——单次检索动辄数千 token，且 80% 可能是噪声；指令相对固定，会话记忆的膨胀速度由回复长度决定（我的实验 8 轮只 +55 tokens，长回复一轮 +145）。

## Q2："上下文快满了怎么办"怎么答？（高频）

**是什么**
答题结构三连：**先反问澄清 → 再分类给解法 → 最后给兜底原则**。
1. 反问：你说的是模型层 Context Window 硬上限，还是应用层内存/token 成本？（展示分层思维，也避免答错方向）
2. 分类解法：五类问题五种解法（见 Q3）。
3. 兜底：**溢出无法 100% 避免**，所以体系必须是"检测 → 降级 → 兜底"三级：检测（预算使用率监控）→ 降级（压缩/RAG 减量）→ 兜底（终止任务开新会话）。

**我的实现**
D2 实现的是第一级"检测"：每轮 `window.check(messages, counter)` 算出使用率，≥75% 触发 `context.near_full` 警告（今天只警告，D3 接压缩即第二级"降级"）：
```python
report = window.check(messages, counter)
logger.info("chat.turn", turn=turn, tokens=report.total_tokens, budget=report.budget, usage_pct=usage_pct, ...)
if report.should_compress:
    logger.warning("context.near_full", usage_pct=usage_pct, threshold=75.0)
```

**面试官会追问什么**
- 追问："为什么阈值定 75% 而不是 90%？" 答：要给当前轮输入输出留余量——LLM 响应本身要占 completion 席位，90% 触发时往往已经溢出；75% 触发、压到 37.5%，一半余量最稳。
- 追问："压缩了还满怎么办？" 答：进入降级链：裁剪工具结果 → 减 RAG Top-K → 简化 system → 终止开新会话（价值从低到高逐级牺牲）。

## Q3：Agent 的上下文问题有哪五类？

**是什么**
①**窗口容量不够**——超长任务/长文档直接溢出，物理装不下。
②**关键信息被淹没**——Lost in the Middle，窗口没满但中间信息"看不见"了。
③**工具返回撑爆上下文**——80% 是噪声：超大 JSON、整文件输出、日志倾倒。
④**多步推理膨胀**——错误推理留在上下文里，越跑越偏（还污染后续判断）。
⑤**多轮对话记忆断裂**——会话长了开头需求被挤出窗口，模型"忘了任务目标"。

**我的实现**
今天直接对抗 ①②③：预算监控（防①）、头尾增强的三段式压缩（D3，防②）、工具结果截断（D4-D5 的 result 截断，防③）。④是 D6 loop 熔断的战场，⑤是 D8 记忆的战场。

**面试官会追问什么**
- 追问："五类问题先解决哪个？" 答：先治③——工具结果是最大且最可控的 token 来源：截断、脱敏、落盘只回引用，收益立竿见影；再治①（预算+压缩），②是模型固有行为只能结构上缓解。

## Q4：什么是 Lost in the Middle？

**是什么**
实证现象（Liu et al. 2023）：模型对窗口**中间位置**信息的关注度天然低于**开头和结尾**——窗口没爆，但信息已经"丢"了。
- 开头（Primer 位置）：任务目标、初始指令——利用率最高。
- 结尾（Recent 位置）：最新对话/工具结果——利用率最高（还有"就近"效应）。
- 中间：历史细节、检索文档——最容易被忽略、被幻觉填充。

**对策**：重要信息放开头/结尾；中间放可丢弃内容（旧历史、低相关文档）；压缩摘要也优先摆到开头位置附近。

**我的实现**
window 侧：`ContextWindow` 只把"总量/预算比"算出来，不知道内容分布——所以 D3 的压缩器把 messages 切成三段：前 3 条 Primers 原样保留、中间摘要、尾部 Recents 保留，天然把"重要指令+最新对话"放两头：
```python
# D3 预告：messages[:3] 保留 + 中间 LLM 摘要 1 条 + messages[-keep_recent:] 保留
```

**面试官会追问什么**
- 追问："Lost in the Middle 怎么验证？" 答：同内容放开头、中间、结尾各测一轮问答准确率，中间显著下降（论文实验做法）；工程上做"压力测试样例"进 eval 集。

## Q5：上下文窗口 vs 注意力跨度？

**是什么**
- **上下文窗口**：模型单次推理"能看见"的最大 token 数——**硬上限**，超过直接报错/截断，由 KV Cache 显存决定。
- **注意力跨度**：看见了之后"能真正专注用好"的范围——软能力，注意力随距离衰减（尤其长文本中段）。

一句话：128K 窗口 ≠ 128K 都能用好；窗口是门票，注意力是观影体验。

**我的实现**
`ContextConfig.context_window_tokens` 是"门票"数值，`ContextWindow.budget = 窗口×0.75` 是"实际保证体验"的安全范围——我把它理解成"注意力可靠区间的近似"：
```python
class ContextWindow:
    def __init__(self, budget: int) -> None: ...
    @classmethod
    def from_model(cls, window_tokens: int, safety_ratio: float = 0.75) -> "ContextWindow":
        return cls(int(window_tokens * safety_ratio))
```

**面试官会追问什么**
- 追问："预算为什么要 < 窗口？" 答：两层含义——给模型输出留 completion 空间；把运营水位压在注意力可靠区，宁可牺牲容量保质量。

## Q6：为什么窗口不能无限大？

**是什么**
三重代价，窗口是"成本旋钮"不是"功能开关"：
1. **计算**：自注意力 O(n²)——长度翻倍，计算量 ×4。
2. **显存**：KV Cache 随长度线性增长，无限窗口 = 显存无底洞。
3. **成本与延迟**：每 token 都要钱和时间，长 prompt 让单次推理变贵变慢。

另外还有"收益递减"：窗口越大，中间信息利用率越低（Q4），100K 里真正有用的可能只有 5K。

**我的实现**
成本意识落地在 `ContextConfig`：窗口、安全系数、压缩阈值全部可配，`ContextWindow.from_model` 一处计算预算，不在代码里裸写数字：
```python
class ContextConfig(BaseSettings):
    context_window_tokens: int = 8192
    safety_ratio: float = 0.75
    compress_threshold: float = 0.75
```

**面试官会追问什么**
- 追问："工程上怎么降低 KV Cache 成本？" 答：输入侧压缩再送模型（本项目的路）、prompt 缓存（供应商侧）、稀疏注意力/线性注意力（模型侧，与我们无关）。

## Q7：token 是什么？怎么估算成本？

**是什么**
- token = 模型处理文本的最小单位。英文约 0.75 token/词，**中文约 1 字 ≈ 0.6-1 token**（按 tokenizer 而定）。
- 成本按 token 计费（prompt + completion 分开计价），**估算必须用真实 tokenizer**（tiktoken / 模型自带），不能拍脑袋数汉字。
- 生产上：客户端计数用 tiktoken 近似，真实用量以 API 返回的 `usage` 字段为准（本项目 `TokenUsage` 就是接 API 的真实数字）。

**我的实现**
`TokenCounter` 双轨制：tiktoken `cl100k_base` 优先，加载失败时回退 `len(text)*0.6` 估算：
```python

        return max(1, int(len(text) * _FALLBACK_TOKENS_PER_CHAR))  # 0.6

    def count_messages(self, messages: list[Message]) -> int:

```
实测：`"你好，世界！这是中英文混合 123 的一段文本。"` 用 tiktoken 数 = 23 tokens（中文≈1.5 字/token，比 0.6 系数估得高，说明 cl100k 对中文偏"费"→ 预算留余量是对的）。

**面试官会追问什么**
- 追问："tiktoken 对 DeepSeek 准吗？" 答：不准——DeepSeek 没有公开 tokenizer，cl100k 只是近似。工程上接受"近似 + 安全余量"（预算×0.75 就是在为近似买单）；精确成本以 API usage 字段结算。
- 追问："中文 1 字几个 token？" 答：常见答案是 0.6-1，但 cl100k 实测中文在 1.5 左右；**说数字前先声明用什么 tokenizer**，不同编码差异很大。

## Q8：什么是 Context Rot / 上下文中毒？

**是什么**
- **Context Rot（上下文腐烂）**：上下文越长，信息利用效率越低（冗余噪声挤压注意力，与 Q4 呼应）——"更大窗口"不是万能药。
- **Context 中毒（中毒）**：幻觉/错误信息进入上下文后，被后续步骤当作事实引用，错误像病毒一样传播（早期错误推理 → 后续推理全部建立在错地基上）。

**结论**：管理上下文（准入、保留、淘汰、更新）比开大窗口更重要；错误信息要**显式标注**（"尝试 X 失败，原因 Y"）而不是清除，清除会丢学习信号。

**我的实现**
D2 的检测层就是"防中毒"的第一道闸：`chat.turn` 事件把每轮 tokens/usage 落日志，一旦使用率异常飙升（某轮工具结果或长回复爆量）能准确定位是哪一份内容进了上下文；错在哪里能被 trace_id 串起来复盘。

**面试官会追问什么**
- 追问："错误的工具调用结果留在上下文里怎么办？" 答：不静默清除——把"参数错误：缺 X"作为 Observation 回给模型让它修正（D4-D5 实践），并在压缩时把失败尝试总结成"教训"留存。

## Q9：什么是上下文配额（预算）管理？

**是什么**
把窗口当 **RAM** 做配额：总预算（= 窗口×安全系数）按份额划分——
- **system 固定份额**：指令+工具 schema，只算一次，通常压到最小（精简描述）。
- **工具 schema 一份**：工具多了会占掉大量预算（>20 个工具 schema 就上千 token）。
- **历史动态份额**：会话越长占越多，是压缩的主要对象。
- **输出余量**：留 25% 给当前轮输入输出（触发线 75% 就是这么来的）。

配套：**监控实际消耗**（每轮计数）、**超 80% 预警**（本项目 75% 触发警告，留 5% 缓冲执行降级）。

**我的实现**
`ContextWindow` = 配额计算器，`ContextReport` = 消耗报告单：
```python
class ContextReport(BaseModel):
    total_tokens: int
    budget: int
    usage_ratio: float
    should_compress: bool          # usage_ratio >= 0.75

class ContextWindow:
    def check(self, messages, counter) -> ContextReport:
        total = counter.count_messages(messages)
        usage = total / self.budget
        return ContextReport(..., should_compress=usage >= COMPRESS_THRESHOLD)
```
`chat.turn` 日志每轮带 `tokens/budget/usage_pct` 三件套，等于给会话装了仪表盘——回放 `chat.log` 就能画出上下文水位线。

**面试官会追问什么**
- 追问："system 的 token 怎么省？" 答：描述精确简短、few-shot 只留必要示例、工具描述合并同类项（>20 工具用渐进披露，D5 主讲）。

## 📊 实验：多轮对话 token 增长曲线

**实验设计**：`python -m afg.chat` 连续多轮对话，每轮日志输出的 usage_pct 绘制曲线。

**实验 1（短回复）**——每轮输入"回应一个词"，模型回复 1-2 字：
```
turn | tokens | usage%
   1 |    31 |   0.5%
   2 |    38 |   0.6%
   3 |    45 |   0.7%
   4 |    52 |   0.8%
   5 |    60 |   1.0%
   6 |    67 |   1.1%
   7 |    73 |   1.2%
   8 |    80 |   1.3%
```
8 轮 31→80，**平均每轮 +7 tokens，完全线性**；按此斜率需约 646 轮才触达 75% 阈值（4608/6144）。

**实验 2（长回复）**——每轮输入"介绍一个水果"，模型回复 3-4 句：
6 轮 177→902，**平均每轮 +145 tokens**，是实验 1 的 20 倍。

**结论（写进笔记的取舍）**
1. **膨胀速度由回复长度控制**——闲聊型任务几乎不涨（+7/轮），信息型任务暴涨（+145/轮），工具结果只会更夸张（D4 后验证）。所以"上下文管理"作用对象永远是后者。
2. **token 统计口径**：session 起始 31 tokens = system prompt（中文）+ 首轮 user 消息，与 tiktoken 计数一致；每轮 usage_pct 与 chat.log 回放完全对齐——日志仪表盘可用。
3. **真实踩坑（网关限流）**：实验第 9 轮起被用户中转网关（CC Switch / 米醋 provider）503 `model:rate_limited` 打断——"发送请求太频繁"。这不是代码 bug 而是外部限流：工程上正是 D6 `with_retry` + 指数退避要解决的事；也提醒"真实 API 调用是有配额账单的"（任务书每日 ≤20 次预算今天就花在这了）。
