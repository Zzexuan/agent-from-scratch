## Q1：RAG 完整流程两阶段？

**是什么**

**离线索引**（加载 → 分块 → 向量化 → 入库）+ **在线检索生成**（query 处理 → 向量检索 Top-K → Rerank → 拼 Prompt → LLM 生成）。分界线是"要不要现场算"：索引一次算完存起来，检索每次都要做。

**我的实现（D9 里可见的证据）**

- 离线索引：`rag/index.py:92` 的 `build_index()`——读目录 → `:112` 分块 → `:116` 向量化 → `:122` 落盘 `search-index.json`
- 在线检索：`rag/index.py:168` 的 `search()`——`:179` 把 query 也编码成向量 → `:180` 算相似度取 Top-K → 拼成文本返回给模型

**真实证据**（首次建索引，7 篇笔记）：

```
rag.index  files=7 chunks=165 embedded=165    第一次：165 块全部要算，耗时 6.4 s
rag.index  files=7 chunks=165 embedded=0      第二次：0 块要算，耗时 0.05 s
```

**面试官会追问什么**

- 追问 1："两阶段里哪一段最贵？" 答：**索引阶段**，因为它要把整个语料过一遍模型。所以才有增量更新（Q7 的追问）——今天 `embedded=0` 就是靠这个：改了哪篇就只重算哪篇。
- 追问 2："为什么检索阶段不存结果？" 答：query 是无限的，存不完；而且**用户问法变了，最相关的块就变了**。

## Q2：为什么说 RAG 是一种特殊的工具调用？

**是什么**

检索功能**就是一个专属工具**：Agent 通过工具调用触发检索、拿到知识、再生成。RAG 解决**知识时效性**（模型不知道你私有的、新的资料），Agent 解决**自主规划**（什么时候该查、查几次）。合在一起就是 Agentic RAG——多轮检索、子问题分解、交叉验证。

**我的实现（D9 里可见的证据）**

这句话在代码里的证明是：**`search_notes` 就是一个普通的 `@tool` 函数，内核里没有任何一行代码知道"RAG"的存在**。

- 工具定义：`tools/search_notes.py:16-17`——`@tool` + `def search_notes(query: str, k: int = 3) -> str:`
- 注册：`demo_rag.py:17` 的 `registry.register(search_notes)`，和 D4 的内置工具**并排注册**（`:14-16` 是 calculator / get_current_time / get_weather）
- 执行：`agents/core.py` 的 ReAct 循环照常 `tool.run(**arguments)`——D4 那条路径一行没改

**真实证据**（`python -m afg.demo_rag`，模型自己决定去查）：

```
agent.start     tool_count=4
tool.call       name=search_notes params={'query': 'function calling 的四步流程', 'k': 5}
agent.observation tool=search_notes result_length=3020
agent.turn      iteration=2 tokens=1404 usage_pct=22.9
agent.done      reason=模型给出最终答案
```

注意 `k=5`：**我没在 prompt 里教它填 5**，是模型读了 schema 自己选的，说明工具描述（docstring）写清楚了。

**面试官会追问什么**

- 追问 1："那 RAG 和工具调用到底差在哪？" 答：**差在触发权**。传统 RAG 是代码写死"先检索再生成"（无条件跑一次）；Agentic RAG 把触发权交给模型——简单问题它压根不查（省一次开销），复杂问题它查好几次。
- 追问 2："那什么时候不该做成工具？" 答：**必须每次都查**的场景（比如合规审查要留痕）就写死在流程里，靠模型自觉反而不可靠。

## Q3：chunk 怎么切？

**是什么**

**语义完整优先**：`chunk_size` 512-1024、`overlap` 100-200；固定长度硬切会拦腰斩断语义。进阶做法是按**文档结构**切（标题/段落），或者用父子块。

**我的实现（D9 里可见的证据）**

我的切法是"**先按结构、超长再按段落**"，两级：

- 一级：`rag/index.py:32` 的 `split_chunks()` 只认 `## ` 开头的行，一个小节就是一个块——因为我的笔记本来就是"一节一问答"
- 二级：`rag/index.py:53` 的 `add_section()` 把超长小节按空行拆段，攒到 `max_chars`（`:59`）就切一刀。`:62` 的注释写了一条纪律：**单个段落自己就超长时不再从中间切断**，宁可这块大一点也不把句子劈两半
- 参数在 `config.py:52` 的 `max_chunk_chars = 800`

**踩到的坑（今天真踩了，记下来）**：第一版把"标题之前的元信息段"也切成块了，结果检索"function calling 的四步流程"时，**排第一的是文件开头的固定格式说明，不是正文**。`:46-49` 改成"有 `##` 标题的文件就跳过标题前那段；整篇没有标题的才退化成整篇一块"。

```
修复前 Top-1：D04-function-calling.md · D04-function-calling   ← 元信息块
修复后 Top-1：D04-function-calling.md · Q1：什么是 Function Calling？标准四步流程？   ✓
```

**面试官会追问什么**

- 追问 1："为什么不做 overlap？" 答：**按结构切就不太需要**——句子不会在标题边界被劈开。overlap 是为"固定长度硬切"兜底的补丁，代价是索引膨胀（重复内容要算多次向量）。真要上固定长度切，我会加 10-20% overlap。
- 追问 2："块太大/太小分别什么后果？" 答：太大 → 一个向量代表太多语义（主题被稀释），而且噪声一起塞进上下文；太小 → 一句话被切碎，检索到也答不出完整信息。我选 800 字符是因为笔记小节多在 1000-3000 字符，切成 2-4 块刚好。

## Q4：Embedding 是什么？双塔（Bi-Encoder）原理？

**是什么**

Embedding 是把文本映射成**高维语义向量**——语义相近的文本，向量方向也相近。**双塔（Bi-Encoder）**指 query 和文档各自独立过同一个编码器，最后才在向量空间里比距离。好处是文档向量可以**离线预计算**；代价是两份文本在编码过程中**从不交互**，所以只能算出"表面语义相似"。

**我的实现（D9 里可见的证据）**

我用的模型是 `BAAI/bge-small-zh-v1.5`，一次前向的完整过程在 `rag/embedder.py:32-44`：

- `:33` 分词（`padding` 补齐、`truncation` 截到模型上限、`return_tensors="pt"` 直接出 PyTorch 张量）
- `:35-38` 前向，输入是 `input_ids` 和 `attention_mask` 两个张量
- `:39` 拿到 `last_hidden_state`，形状是 `(条数, token 数, 512)`
- `:42` **取 CLS 位**当整句的代表（BGE 的约定，不是把各 token 平均）
- `:43` L2 归一化 → 之后**余弦相似度就等于点积**，`index.py:132` 的 `dot()` 一个乘法累加就够了

**"模型前向发生在哪"**：`:35` 这一行调用的是 `transformers` 里的 PyTorch 模型，真正的矩阵运算在 **torch 的 C++ 扩展**里（`torch_cpu.dll`，258MB）——**这部分代码不在我项目里，我项目里只有"怎么调它"**。这在 RAG 里叫"编码器是外部依赖"，生产中它要么是本地推理服务、要么是 embedding API。

**真实证据**（冒烟测试，离线加载）：

```
hidden_shape (3, 11, 512)     3 句话、最长 11 个 token、每 token 512 维
vector_shape (3, 512)         每句话压缩成 1 个 512 维向量
norm 1.0                      归一化后模长是 1
```

**面试官会追问什么**

- 追问 1："为什么取 CLS 而不是平均池化？" 答：**看模型怎么训练的**。BGE 训练时就用 CLS 位接对比学习的目标函数，所以推理时必须用 CLS——换成平均池化是"用错模型的输出"，效果会掉。反过来，有些模型（如部分 e5 系）训练时用平均池化，那就不能取 CLS。**结论：池化方式是模型的合同，不是自由选项。**
- 追问 2："双塔快，为什么还需要 Cross-Encoder？" 答：见 Q5/Q6——双塔的"快"是拿"不交互"换来的。
- 追问 3："512 维是怎么来的？" 答：`config.json` 里的 `hidden_size`，是模型结构定的，训练时定死；维度越大表达能力越强，但索引也跟着线性变大。

## Q5：相似 ≠ 相关是什么意思？

**是什么**

Embedding 算的是**表面语义相似**，不是"能不能回答这个问题"。经典反例："大连医科大学怎么样" 会召回 "大连理工大学怎么样"——两句话几乎同构，但答非所问。**相关 = 能否回答问题**，这是精排（Rerank）要解决的问题。

**我的实现（D9 里可见的证据）**

今天我亲手摸到了三个"相似≠相关"的实例：

1. **元信息块排第一**（Q3 那个坑）——它和 query 的向量相似度 0.6769，比真正回答问题的 Q1（0.6769 的下一名）还高。字面像，但没内容。
2. **同一个小节占满 Top-3**——第一版里问 "function calling 的四步流程"，返回的三条里有两条是**同一小节被切开的两半**，第三条才是别的。相似度都对，但信息重复。
3. **语义漂移**：问"什么是上下文压缩"，Top-1 是 `D03 · Q5：什么时候触发压缩？`，虽然同一篇、也算相关，但**不是**直接回答"什么是"的那一节。

针对 2 我做了处理：`rag/index.py:152-156` 按 `source|title` **去重**，一个小节只留最相关的那一块。针对 1 是改分块（Q3）。**针对 3，我今天没有解法——它正是 Rerank 要上场的地方。**

**面试官会追问什么**

- 追问 1："相似度能当阈值用吗？" 答：**谨慎**。上面第 1 条就是例子：一个高相似度的块可能毫无信息量。而且不同模型的相似度分布完全不同（BGE 高分能到 0.9，有的模型 0.5 就算高），阈值必须**在自己的语料上标定**，不能抄别人的数。
- 追问 2："那你怎么判断检索失败？" 答：今天靠人眼看 Top-1 是不是对的那一节。要自动化就得上 Q9 的评估指标。

## Q6：Rerank（Cross-Encoder）为什么有效？为什么不直接全用它？

**是什么**

Cross-Encoder 把 query 和文档**拼成一个输入送进模型**，让它们在每一层内部逐层交互——所以它能判断"这段到底能不能回答这个问题"，而不只是"长得像不像"。但代价是：**每对 (query, 文档) 都要现场算一次前向**，没法预计算。所以生产上是两阶段：粗排召回 Top100（快）→ 精排取 Top5（准）。

**我的实现（D9 里可见的证据）**

**今天我只有粗排，没有精排**，这一点必须说清楚：

- 粗排：`rag/index.py:139` 的 `cosine_top_k()`——纯点积 + 排序，`O(块数)`，165 个块是 165 次乘法累加，**不用过模型**
- 精排：**没有**。模型只在 `:179` 编码了 query 一次

也就是说，我的检索质量**全部押在"向量相似度靠谱"这个假设上**——Q5 的三个实例说明这个假设是有漏的。精排本该是补齐它的那一环。

**面试官会追问什么**

- 追问 1："为什么不全用 Cross-Encoder？" 答：算不过来。Cross-Encoder 需要**每个候选过一次模型**——100 个候选就是 100 次前向，而双塔只要 1 次（query）+ 0 次（文档已离线算好）。这是**精度和延迟的取舍**：双塔负责把"上万块"筛到"上百块"，Cross-Encoder 才有资格在这上百块里做精细判断。
- 追问 2："Top-K 的 K 该设多少？" 答：粗排的 K（召回）和精排的 K（喂给 LLM）是两个参数。粗排 K 太小会把正确答案漏在门外（**精排救不回没召回的**），太大则精排开销和上下文都吃不消。我今天是 3 或模型自己选的 5。
- 追问 3："BGE 有没有提精排模型？" 答：有，`bge-reranker` 系列就是配套的 Cross-Encoder。换成本地模型的话，同一个 `models/` 目录下再加一个 reranker 就能接上，`embedder.py` 的形状不用改。

## Q7：提升 RAG 检索准确率的方法（至少 3 个）？

**是什么**

混合检索（BM25 + 向量，召回率可 +17%）、Query Rewrite（口语 → 专业表述）、Rerank 精排、HyDE（先让 LLM 写一个假想答案再拿去检索）、调 chunk 策略。**注意分层次**：前三个分别作用在"召回"、"query 侧"、"精排"，不要混着背。

**我的实现（D9 里可见的证据）**

今天做了 **1.5 个**——诚实盘点：

1. **Query 侧加前缀**（`rag/index.py:9-10` 的 `QUERY_PREFIX`）。BGE 这类模型是**非对称编码**：文档侧不加前缀，query 侧加"为这个句子生成表示以用于检索相关文章："，让问题和答案在向量空间里靠得更近。代码里就是 `:179` 的 `QUERY_PREFIX + query`——**一行字符串拼接，但它是官方推荐的用法**。
2. **分块策略**（Q3）——算半个，因为它是"调 chunk 策略"那条。

**没做的**：混合检索（要引 BM25，得自己写倒排索引）、Rerank（Q6）、HyDE（多一次 LLM 调用，要花钱）、Query Rewrite。

**面试官会追问什么**

- 追问 1："这五个里，只能选一个先上，你选哪个？" 答：**看当前瓶颈在召回还是在精排**。先用 Q9 的指标量一下：如果 Top-100 里根本没有正确文档 → 瓶颈在召回，上混合检索；如果正确文档在 Top-100 但没进 Top-5 → 瓶颈在精排，上 Rerank。
- 追问 2："混合检索为什么有效？" 答：**向量和关键词是两种盲区互补的检索方式**。向量强在语义改写（"怎么让模型别乱编" ↔ "幻觉防范"），但**对专有名词、编号、代码标识符很弱**——比如查 `tool_call_id`，BM25 一次就精确命中，向量可能召回一堆讲"工具调用"的段落。反过来 BM25 完全不懂同义改写。
- 追问 3："Query Rewrite 在什么场景收益最大？" 答：**用户话很少、很口语**的时候（"那个报错咋回事"）。多轮对话里更明显：需要把"它呢？"补全成"XXX 呢？"再检索。

## Q8：RAG 内容缺失/答非所问怎么排查？

**是什么**

**三步定位，别先怪模型**：查切块（语义被斩断了？）→ 查召回（纯向量跑偏？上混合检索）→ 查精排（Rerank 兜底）。因为这三步是**串联**的，前面一步坏了，后面再强也白搭。

**我的实现（D9 里可见的证据）**

今天的三次排查，正好覆盖了前两步：

| 现象 | 查了哪一步 | 结论与动作 |
|---|---|---|
| Top-1 是"固定格式说明"那块 | **查切块** | 元信息被当成正文切进来了 → `index.py:46-49` 跳过标题前内容 |
| Top-3 里两条是同一小节 | **查切块 + 查排序** | 一个小节切成了多块 → `index.py:152-156` 按小节去重 |
| 问"什么是上下文压缩"，Top-1 是"什么时候触发压缩" | **查召回** | 向量把"同一主题的不同问题"混在一起了；精排没上（Q6），这就是它的位置 |

**排查要用的抓手**：我每个块都带 `source` 和 `title`（`index.py:28-29` 的 `make_chunk`），所以**看一眼来源就知道是切错了还是召回错了**——这也是给 LLM 的返回值里必须带出处的原因（`tools/search_notes.py:10`）。

**面试官会追问什么**

- 追问 1："怎么快速判断是切块问题还是模型问题？" 答：**把正确的原文直接塞进 prompt 试一次**。如果答案就对了 → 检索/切块的问题；如果还是错 → 才是模型的问题（或者 prompt 的问题）。这一步能立刻把锅定位到正确的环节。
- 追问 2："怎么知道'召回里到底有没有正确答案'？" 答：人工标注一个小评测集（问题 → 正确文档 id），然后看 `Recall@K`。**没有这个集合，'召回不准'就是个感觉，不是结论。**

## Q9：RAG 效果怎么评估？

**是什么**

**三层指标**，一层比一层接近最终效果：

- **检索层**：Hit Rate / MRR / Recall@K——正确答案在不在召回里、排第几
- **忠实度（Faithfulness）**：答案有没有脱离检索到的上下文（**在编**就是 0 分，哪怕答得漂亮）
- **答案质量**：ROUGE-L / 人工评

核心认知：**评估自动化，才能持续迭代**。手动看几条"感觉不错"是没法用来做 A/B 对比的。

**我的实现（D9 里可见的证据）**

我今天**只做了最原始的人工验证**，自动化一条没做，如实记录：

- 人工验证：`python -m afg.demo_rag` 的输出里，`top_source=D04-function-calling.md`，最终答案也标了 `D04 · Q1` —— **检索层对了，引用也可溯源**

## Q10：为什么 RAG 要用向量数据库而不是 MySQL？

**是什么**

向量检索需要**专门的 ANN 索引**（HNSW / IVF）——先建近邻图再近似查找，把"和全库每条算一遍"降到"只探几条路径"。MySQL 没有这种索引，只能全表扫 + 逐条算余弦，几万条就崩了。**但元数据过滤（时间、来源、标签）仍常配合关系库或表字段来做。**

**我的实现（D9 里可见的证据）**

我的实现是"**最朴素的暴力检索**"，正好反证了上面这段：

- 打分：`rag/index.py:141-143` 对**每一个块**都算一遍点积，然后 `:144` 全排序——**这是 O(N)，就是 MySQL 全表扫那条路**
- 规模：`rag.index chunks=165` —— 165 维乘加是微秒级，暴力扫完全够用，**所以今天不需要向量库**
- 元数据：块里带了 `source`（文件名）当过滤维度（`index.py:28`），只是今天没用它过滤

**什么时候必须换**：块数到了**十万到百万**量级，全扫就从微秒变成秒级了。那时才需要 ANN 索引，典型选择是 FAISS（本地库）/ Milvus、Qdrant（服务）。

**面试官会追问什么**

- 追问 1："ANN 是精确的吗？" 答：**不是，是近似的**——用一点召回率换数量级的速度。所以引入 ANN 之后 Q9 的 Recall@K 会掉一点，这是必付的账，要靠把 `ef_search` / `nprobe` 这类参数调大来买回来。
- 追问 2："不用向量库，只用 FAISS 行不行？" 答：**行，而且很多场景就该这样**。FAISS 是库不是服务，没有并发、持久化、过滤、增删的工程封装。要不要上服务，取决于**是否多进程/多机共享、是否需要按权限过滤、是否需要在线增删**。
- 追问 3："那 SQLite 加个向量扩展呢？" 答：有（sqlite-vec 之类），适合"数据量不大 + 已经用 SQLite"的场景。**选型的判断标准始终是规模和数据形态，不是哪个更时髦。**
