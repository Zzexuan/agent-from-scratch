## Q1：Agent 怎么做工具选择？有哪些策略？（高频）

**是什么**

四种策略，工程上组合使用：

| 策略 | 做法 | 代价 |
|---|---|---|
| **全量注入** | 所有工具的 schema 都塞进请求 | 简单，但吃上下文；工具多了模型也选不准 |
| **渐进披露** | 先只给工具名 + description，需要时再加载完整 schema | 省 token，但要两轮交互 |
| **语义检索** | 工具描述向量化，按任务取 Top-K 再注入 | 准确率高（论文里报过 3 倍提升），但要维护向量库 |
| **分层路由** | 先用一个小模型分类，再加载对应工具集 | 准确，但多一次调用 |

**我的实现（D5 里可见的证据）**

D5 用的是**全量注入**——三个工具的 schema 全塞进每次请求：

`demo_registry.py:22-30` 把注册器的 schema 全打出来：
```
registry.schema  tool=calculator
registry.schema  tool=get_current_time
registry.schema  tool=get_weather
```

真实成本：`prompt_tokens=489`（第一次请求只带了 1 条 user 消息，对话本身才十几个字），**这 489 个 token 里绝大部分是三个工具的 schema**。

`tools/registry.py:25-29` 的 `to_openai_schemas()` 就是"全量注入"的实现——它把注册器里所有工具一次性吐出来。**要改成渐进披露或语义检索，就是改这一个方法。**

**面试官会追问什么**

- 追问 1："三个工具就全量注入，工具多了怎么办？" 答：经验值 **超过 20 个工具选择准确率明显恶化**（见 Q2）。我的项目现在 3 个，到 D10 加 Skills、D11 加 MCP 之后工具数会上去，那时 `to_openai_schemas()` 就要改成"按任务筛 Top-K"——**接口已经留好了，改这一个方法就行**。
- 追问 2："分层路由为什么能提升准确率？" 答：因为它把"从 50 个工具里选"变成了"先从 5 个类别里选，再从 10 个工具里选"——**每次决策的候选集小了，模型不容易选错**。代价是多一次分类调用（可以塞给小模型，便宜）。

- 腾讯云《160+ 真题》Q6-Q15
- 知乎《2026 Agent 大厂面试题汇总》"工具选择策略"节

## Q2：工具太多会发生什么？

**是什么**

三个连锁恶化：

1. **描述重叠 → 模型困惑选错**（两个工具都能"查信息"，它就瞎选）
2. **schema 占满上下文**（每个工具的 schema 几百 token，50 个工具就几万）
3. **选择准确率下降**（经验值 **>20 个明显恶化**）

三个解法：**合并同类工具**（`get_user_info` + `get_user_orders` → 一个带 type 参数的）、**渐进披露**、**RAG 选工具**。

**我的实现（D5 里可见的证据）**

D5 的注册器把这个问题**变成可观测的**：

`tools/registry.py:22-23`
```python
    def names(self):
        return list(self._tools.keys())
```
`demo_registry.py:37` 打出来：
```
registry.start  tools=['calculator', 'get_current_time', 'get_weather']
```

三个工具名一眼可数。**等这个列表长到 20 个以上时，日志里就能直接看到，而不是等到模型选错才发现。**

另外 `tools/registry.py:9-12` 的重名检查防止了"两个工具同名"这种最恶性的重叠：
```python
    def register(self, tool):
        if tool.name in self._tools:
            raise DuplicateToolError("工具名重复，已经注册过了", context={"tool": tool.name})
```

**面试官会追问什么**

- 追问 1："怎么判断两个工具描述重叠了？" 答：**看它们在什么问题上会同时被选中**。我的做法是把工具描述拿出来对比"边界句"——比如 `get_weather` 写了"目前只支持北京、上海、深圳三个城市"，如果再加一个 `get_air_quality` 也查这三个城市，模型就可能在"深圳天气"上选错。**判断标准：一个用户问题如果两个工具都"看起来能答"，就是重叠。**
- 追问 2："合并同类工具有什么代价？" 答：**参数变复杂**。合并后要加一个 `type` 参数让模型指定要查什么，模型可能选错 type。所以合并不是无脑合——**"同源数据、同一权限、同一超时"的工具才合并**。

## Q3：如何设计高质量的工具描述？

**是什么**

四条：

1. **功能精准具体**
2. **明确边界**（"只做什么 / 不做什么"）
3. **参数说明带类型与示例**
4. **避免功能重叠的两个工具**

**描述质量直接决定调用准确率**——D4 已经用真实运行验证过一次。

**我的实现（D5 里可见的证据）**

D5 把这些要求**固化进了装饰器的机制**里——不是靠自觉，是靠代码强制：

`tools/decorator.py:134-139`
```python
def tool(fn):
    description = first_paragraph(fn.__doc__)
    if not description:
        raise TypeError("工具 " + fn.__name__ + " 缺少 docstring，没法生成 description")
    schema = build_parameters(fn)
    return FunctionTool(fn, fn.__name__, description, schema)
```

`decorator.py:136-137`：**没有 docstring 就不许注册**。想加工具？先把描述写好。

`tools/builtin.py:71-76` 的天气工具是"边界写清楚"的正面例子：
```python
@tool
def get_weather(city: str) -> str:
    """查询一个城市的当前天气，返回天气状况、气温和湿度。
    目前只支持北京、上海、深圳三个城市，其他城市会返回错误。

    :param city: 中文城市名，可选值：北京、上海、深圳
    """
```

**参数描述也在里面**（`:param city:` 那行），由 `decorator.py:29-42` 的 `parse_param_descriptions()` 解析进 schema。

**真实证据（D4 已验证过一次）**：问"火星的天气"，模型读了"只支持三个城市"这句，**主动放弃调用**并解释原因。**这不是我教的，是描述在起作用。**

**面试官会追问什么**

- 追问 1："描述写多长合适？" 答：**够写清边界就行**。我实测的经验：三个工具 schema 加起来约 480 token（`prompt_tokens=489` 减去对话本身）。description 写太长，每次请求都在烧钱——**描述是要进每一轮上下文的，不是写一次就完了**。
- 追问 2："参数描述也要写吗？能省吗？" 答：不能省。`tools/builtin.py:75` 的"可选值：北京、上海、深圳"直接把枚举值给了模型，**挡掉了大部分无效调用**。省了这行，模型就可能传"广州"进来吃错误——多一次无效往返的成本远高于这一行的 token。

## Q4：什么是工具调用幻觉？怎么防范？

**是什么**

两种表现：
1. **调不存在的工具**（把 `get_weather` 说成 `get_temperature`）
2. **传错参数**（缺必填、类型不对、传了不存在的参数名）

五种防范手段：

| 手段 | 作用 |
|---|---|
| 严格 schema 校验 | 参数层拦截 |
| **工具名白名单** | 名字层拦截 |
| **未知工具直接报错回给 LLM**（不要猜） | 不猜、不静默失败 |
| 参数强校验 | 类型/必填层拦截 |
| 频率限制 | 防死循环（D6 的熔断） |

**我的实现（D5 里可见的证据）**

**名字层**：`tools/registry.py:14-20`
```python
    def get(self, name):
        if name not in self._tools:
            raise UnknownToolError(
                "没有这个工具",
                context={"tool": name, "available": list(self._tools.keys())},
            )
        return self._tools[name]
```
**注意 `context` 里带了 `available`**——所有可用工具的名单。这个字段的用处见下面的真实证据。

**参数层**：`tools/decorator.py:87-100` 的 `check_arguments()`，三类问题全拦：
```python
    for name in required:
        if name not in kwargs:
            return "缺少必填参数 " + name
    for name in kwargs:
        if name not in properties:
            return "不支持参数 " + name + "，可用参数：" + available
        expected = properties[name]["type"]
        if not type_matches(expected, kwargs[name]):
            return "参数 " + name + " 类型不对，应该是 " + expected
```

**⚠️ 这是 D5 修掉的一个真 bug**：D4 的 calculator 里是 `expr = kwargs["expr"]`，模型**没给** `expr` 时抛的是 `KeyError`，而调用方只 `except ToolError`——**抓不住，程序直接崩**。D4 没暴露是因为模型每次都乖乖给了参数。现在统一在 `FunctionTool.run()` 里预检，所有 `@tool` 工具自动受保护。

**真实证据（幻觉防范的正面验证）**：

`demo_registry.py:40-49` 模拟模型点名一个不存在的工具：
```
registry.hallucination  tool=delete_file  call_id=call_fake_1
registry.unknown_tool   message=工具不存在：delete_file。可用工具：calculator、get_current_time、get_weather
```

把这个错误包装成 `role="tool"` 消息回填后，模型的回答（真实抓取）：
```
我没法帮你删掉 a.txt —— 我这边并没有 `delete_file` 这个工具。
我目前可用的工具只有三个：
- `calculator`：计算数学表达式
- `get_current_time`：获取当前日期时间
- `get_weather`：查询北京/上海/深圳的天气
也就是说，我没有文件系统访问能力，既不能删除文件，也不能读取或修改文件。
如果你想删掉 a.txt，需要在本地终端里执行 `rm a.txt`...
```

**三个关键点**：①它承认工具不存在；②**它列出的能力清单和 schema 里完全一致**（没编）；③它没假装"删除成功"，而是给了真实替代方案。

**面试官会追问什么**

- 追问 1："为什么不直接猜一个最像的工具去调？" 答：**猜错比不调更糟**。猜着调会执行一个错误的动作（比如用户要查天气，你调了计算器），产生的副作用可能不可逆。而且**把错误明确回给模型，它自己会纠正**——上面那段回答就是证据。这就是"错误也是 Observation"。
- 追问 2："参数校验为什么不用 pydantic？" 答：**因为我这里不需要它的模型定义开销**。json_schema 里已经有类型信息，我直接按 schema 逐项比对就够了（`decorator.py:69-84` 的 `type_matches`）。**pydantic 更适合"有嵌套结构、有复杂校验规则"的场景**（比如 D1 的 `Message`），工具参数是扁平的基本类型，手写更透明。
- 追问 3（我修的 bug 引出）："`bool` 是 `int` 的子类，这会有什么坑？" 答：**有**。`decorator.py:72-75` 专门处理了：判断 integer 时先检查 `isinstance(value, bool)` 并返回 False，否则 `True` 会被当成合法的整数参数。**这个坑和 D4 的 `calculator` 里拦 `True + True` 是同一个原因。**

## Q5：工具调用失败的错误处理最佳实践？

**是什么**

**先分类，再处理**：

| 类型 | 例子 | 处理 |
|---|---|---|
| **可重试** | 网络超时、限流 429 | 指数退避重试（代码层面自动做） |
| **不可重试** | 参数错、业务规则不满足 | **把错误信息作为 tool 结果回给 LLM**，让它自己改 |

核心原则：**错误也是 Observation。把"失败"交给模型反思，比静默重试好。**

为什么？因为模型看到错误能做出代码做不到的判断——比如它可能意识到"用户其实想要另一个工具"，或者"这个参数应该换个值"。

**我的实现（D5 里可见的证据）**

D5 的做法是**工具抛异常、调用方包装回填**，职责清晰：

**工具侧**（`tools/decorator.py:113-119`）——只负责抛出，带足上下文：
```python
    def run(self, **kwargs):
        problem = check_arguments(self._schema, kwargs)
        if problem:
            raise ToolError(
                "参数错误：" + problem,
                context={"tool": self.name, "arguments": kwargs},
            )
```

**调用方侧**（`demo_fc.py:57-62`）——捕获并包装成人话：
```python
        try:
            tool = registry.get(tc.name)
            result = tool.run(**tc.arguments)
        except AfgError as e:
            result = "工具执行失败：" + str(e)
            logger.warning("fc.tool_error", tool=tc.name, error=str(e), context=e.context)
```

**注意这里捕的是 `AfgError` 不是 `ToolError`**——因为要同时覆盖 `UnknownToolError`（名字错）和 `ToolError`（参数错/执行失败）。两者都是 `AfgError` 的子类，**这个层次结构就是为这一刻设计的**（D4 建的）。

`demo_fc.py:61` 的 `result = "工具执行失败：..."` 就是"把错误变成 Observation"——它会被 append 成 `role="tool"` 消息，模型下一轮就看到它了。

**真实证据**：D4 实测过——强制模型查不存在的城市广州，工具抛 `ToolError`，模型收到错误后说"我不能编造一个广州的天气结果给你"，并给出替代方案。

**面试官会追问什么**

- 追问 1："可重试的错误谁来重试？工具层还是调用层？" 答：**调用层（或更外层的 HTTP 客户端）**，不能在工具层重试。因为工具层的重试会阻塞整个循环，而且它不知道"还要不要继续这个任务"。D6 的 `with_retry` 装饰器会加在 LLM 调用那一层。
- 追问 2："错误信息写多详细？会不会泄露内部结构？" 答：**给模型看的要详细到能纠正**（"缺少必填参数 expr"够它改），**但不要泄露内部实现**（不要说"第 42 行 KeyError"）。我的做法是错误信息面向"用户能理解的话"，技术细节放 `context` 字典里进日志——**两个受众分开**。

**参考来源**
- 腾讯云《160+ 真题》错误处理题

## Q6：before_tool_call / after_tool_call 钩子有什么用？

**是什么**

在工具调用的**前后**插入统一的处理点：

| 钩子 | 做什么 |
|---|---|
| **before** | 参数校验、鉴权、限流、日志 |
| **after** | 结果脱敏、格式转换、长度截断、性能统计 |

价值在于**横切关注点集中化**——不用在每个工具里重复写"记日志""脱敏"，写一次对全部工具生效。这是 AOP（面向切面）在 Agent 里的落地。

**我的实现（D5 里可见的证据）**

**D5 的 `FunctionTool.run()` 就是一个"before + after"的合并实现**——所有 `@tool` 工具自动带上：

`tools/decorator.py:113-131`
```python
    def run(self, **kwargs):
        problem = check_arguments(self._schema, kwargs)     # ← before：参数校验
        if problem:
            raise ToolError("参数错误：" + problem, context={...})

        logger = get_logger("tool")
        started = time.perf_counter()
        result = str(self._fn(**kwargs))                    # ← 调用真身
        logger.info(                                         # ← after：性能统计 + 日志
            "tool.call",
            name=self.name,
            params=kwargs,
            result_length=len(result),
            latency_ms=round((time.perf_counter() - started) * 1000, 1),
        )
        return result
```

**这就是"装饰器模式"的核心好处**：`tools/builtin.py` 里那三个函数**只写了业务逻辑**，一行日志、一行校验都没有——但每个工具调用都自动有了。对比 D4：那时日志是写在 `demo_fc.py` 的调用点上，**只有这一个调用点有日志**；现在日志长在工具身上，**谁调都有**。

**真实证据**（`demo_fc` 跑天气的真实日志，注意多出来的 `tool.call`）：
```
fc.tool_request  tool=get_weather arguments={'city': '深圳'} call_id=call_00_umb...
tool.call        name=get_weather params={'city': '深圳'} result_length=23 latency_ms=0.0   ← D5 新增
fc.tool_call     tool=get_weather arguments={'city': '深圳'} result_length=23 latency_ms=0.3
```

`tool.call` 是工具自己打的（D5），`fc.tool_call` 是调用方打的（D4）——**两层视角**：前者答"工具自己花了多久"，后者答"从发起到拿到结果一共多久"（含注册器查找）。

**面试官会追问什么**

- 追问 1："鉴权钩子怎么写？" 答：现在是**没有**的（本地工具不需要）。要做的话是在 `run()` 里校验"当前用户有没有权限调这个工具"，或者按工具分级（读类工具放开、写类工具要确认）。**D13 的沙盒护栏就是这个模式的完整版**（超时/黑名单/输出截断全在这个位置做）。
- 追问 2："钩子会不会拖慢调用？" 答：会，但可忽略——`latency_ms=0.0` 说明日志+校验的开销在 0.1ms 以下，而一次 LLM 调用是 **1575ms**（真实数据）。**差距是四个数量级**，优化钩子没有意义。真正该优化的是上下文长度（每次请求 489~560 token 的 schema）。

## Q7：工具结果的清理机制？

**是什么**

四件事（和 D4 的 Q8 接上）：**长度截断、敏感信息脱敏、大结果压缩或落盘只回引用、格式规范化**。

最后一条容易被忽略：**大输出不要塞进上下文，而是存成文件、只把路径给模型**——模型需要时再让别的工具去读。这样上下文里只有一行路径，而不是几万行日志。

**我的实现（D5 里可见的证据）**

D5 只做了**可观测**，没做清理——因为三个内置工具的输出都极短：

`tools/decorator.py:124-130` 记了 `result_length`，这就是"将来该截断谁"的依据：
```python
        logger.info(
            "tool.call",
            name=self.name,
            params=kwargs,
            result_length=len(result),
            latency_ms=...,
        )
```

真实数据（三个工具跑下来）：
```
tool.call  name=calculator        result_length=4
tool.call  name=get_weather       result_length=23
tool.call  name=get_current_time  result_length=19
```
**最长 23 个字符**，离需要截断还差三个数量级。

**面试官会追问什么**

- 追问 1："那你现在做清理了吗？" 答：**没做，而且我知道为什么现在不做**。清理的动机来自"工具输出可能很大"——而 D5 的三个工具都是本地秒回的小输出。真正需要它的是 D13 的 `exec_command`（能返回几万行命令输出）。**提前做等于空转**，但 `result_length` 字段现在就在，D13 一接上立刻能看到谁超标。
- 追问 2："截断的阈值定多少？" 答：看模型窗口。我这里的实验窗口是 8192，所以工具输出绝对不能超过几百 token——**阈值该按窗口百分比定，不是拍一个固定数字**。这也是为什么 `config.py` 里那些参数都放配置而不是硬编码。

## Q8：为什么用装饰器注册工具？好处？

**是什么**

三条好处，正好对应"手写注册"的三个痛点：

| 好处 | 解决的问题 |
|---|---|
| **声明式**（写函数 = 注册工具） | 不用再写一遍 `registry.register(XxxTool())` |
| **docstring / 类型注解是单一真源** | **手写 schema 会和实现漂移** |
| **可统一加钩子** | 校验/日志/脱敏写一次全生效（见 Q6） |

第二条是最值钱的：手写 schema 时，你把参数名改成 `expression`，schema 里还写着 `expr`——**代码能跑，但模型永远传不对参数**。

**我的实现（D5 里可见的证据）**

**迁移前（D4 手写）**——schema 和实现在两个地方：
```python
class CalculatorTool(BaseTool):
    name = "calculator"
    description = "计算一个数学表达式的值。参数 expr 是表达式字符串，..."
    def parameters(self):
        return {"properties": {"expr": {"type": "string", ...}}, "required": ["expr"]}
    def run(self, **kwargs):
        expr = kwargs["expr"]
```

**迁移后（D5 声明式）**——一处写完，schema 自动生成：
```python
@tool
def calculator(expr: str) -> str:
    """计算一个数学表达式的值。支持加减乘除、取余、乘方和括号，例如 37*89 或 (1+2)*3。
    只能算纯数字，表达式里不能出现变量名或函数调用。

    :param expr: 要计算的数学表达式，例如：37*89
    """
    ...
```

**41 行 → 11 行**（三个工具合计从 128 行降到 91 行），而且参数名只有一处。

**真实证据（schema 质量不退化）**：我用注册器打印了自动生成的 schema，和 D4 手写的逐字段比对——**结构完全一致**，`required`、参数 `description` 都在。过程中发现并修掉一个退化：多行描述被拼接时多出一个空格，改成保留换行。

**面试官会追问什么**

- 追问 1："装饰器读的是类型注解，那注解在 Python 里到底起什么作用？" 答：**平时它只是给人和工具看的提示，运行时几乎被忽略**——D1-D4 的注解就是这样，删掉程序照跑（我 D1-D4 甚至一度全删过）。**D5 是注解第一次真的被程序读取并使用**：`decorator.py:51` 的 `TYPE_TO_JSON.get(param.annotation)`。这是理解"注解不只是注释"的最好例子。
- 追问 2："装饰器会不会让调试变难？" 答：**会，而且我正好绕开了这个坑**。标准装饰器写法是"返回一个包装函数"，那样 `calculator.__name__` 会变成包装函数的名字、`__doc__` 也丢了——所以要用 `functools.wraps` 把元数据抄回来。**我的设计是 `@tool` 返回一个 `FunctionTool` 对象而不是包装函数**（`decorator.py:139`），压根不存在"元数据丢失"，所以不需要 `functools`。代价是 `calculator` 不再是可调用函数而是工具对象——这正好是我要的。
- 追问 3："那什么时候必须用 functools.wraps？" 答：**装饰器返回包装函数时**。比如你要加一个 `@log_calls` 装饰器打印每次调用，就必须 `@functools.wraps(fn)`，否则原函数的 `__name__`/`__doc__` 会丢，pytest 收集测试、Sphinx 生成文档都会出问题。

- 腾讯云《160+ 真题》装饰器注册题
- 主文档《核心接口规格》工具系统节

## Q9：并行工具调用怎么在注册器层面支持？

**是什么**

注册器层要满足两个条件：

1. **`get(name)` 幂等无状态** —— 多个线程同时查同一个工具必须安全
2. **按 `id` 回填** —— 执行顺序不影响结果对应关系

外加一个警告：**有副作用的工具要考虑并发安全**（两个线程同时写同一个文件）。

**我的实现（D5 里可见的证据）**

**条件 1 天然满足**：`tools/registry.py:14-20` 的 `get()` 只做一件事——从字典里读：
```python
    def get(self, name):
        if name not in self._tools:
            raise UnknownToolError(...)
        return self._tools[name]
```
**它不修改任何状态**，所以多线程同时调它绝对安全。整个注册器的写操作只有 `register()`（`registry.py:9-12`），而注册是启动时一次性的（`demo_fc.py:15-20` 的 `build_registry()`）。

**条件 2 由消息层保证**：`demo_fc.py:71` 是 `tool_call_id=tc.id`，**写在循环体内、每个工具单独 append**。所以将来换成线程池，回填顺序变了也不影响——**对应关系靠 id，不靠数组顺序**。

**真实证据（D5 的多个 tool_call 结构）**：
```
fc.tool_request  tool=get_weather  arguments={'city': '深圳'}  call_id=call_00_umb...
```
每个请求都带独立 `call_id`。`demo_fc.py:53` 的 `for tc in resp.tool_calls:` 说明响应本来就可以有多个。

**面试官会追问什么**

- 追问 1："字典在 Python 里线程安全吗？" 答：**单个读操作是安全的**（GIL 保护），但"检查再读"（先 `in` 再 `[]`）这种复合操作在多线程下不是原子的。我的 `get()` 有 `if name not in self._tools` 再 `return self._tools[name]` —— **严格说存在竞态**，但因为注册器只在启动时写、运行时只读，实际不会出问题。要严格的话加个锁，但那是过度设计。
- 追问 2："什么工具不能并行？" 答：**有副作用且共享资源的**。比如两个工具都往同一个文件写日志、都改同一个数据库行。我的三个工具都是纯读（计算器甚至无状态），所以并行完全安全。**将来接 `exec_command`（D13）就要小心**——两条命令同时改一个文件就是竞态。

**参考来源**
- OpenAI 并行工具调用文档
- 主文档 D16 规格（线程池 + 超时 + 失败聚合）

## Q10：tool 层怎么定义、运行时怎么被调用？（字节真题）

**是什么**

这条链路能讲清，就说明真做过：

```
定义：函数/类 + schema 元数据 → 注册进 registry
运行：LLM 返回 tool_call → registry 查名字 → 参数校验 → 执行 → 结果包装成 tool 消息回填
```

**我的实现（D5 里可见的证据）**

**定义阶段**（`tools/builtin.py`，装饰器自动完成）：
```
@tool                    → decorator.py:134  读 docstring + 注解
def get_weather(...):    → decorator.py:138  build_parameters() 生成 schema
                         → decorator.py:139  返回 FunctionTool 对象
```
然后 `demo_fc.py:15-20` 的 `build_registry()` 把三个工具塞进注册器。

**运行阶段**（`demo_fc.py:53-71`）：
```
demo_fc.py:58      registry.get(tc.name)      ← ① 查名字（未知就抛 UnknownToolError）
decorator.py:114   check_arguments(...)       ← ② 参数校验（在 FunctionTool.run 内部）
demo_fc.py:59      tool.run(**tc.arguments)   ← ③ 执行
demo_fc.py:71      role="tool" 消息回填        ← ④ 包装回填
```

**真实日志（完整链路一次跑通）**：
```
fc.tool_request  tool=get_weather  arguments={'city': '深圳'}  call_id=call_00_umb...
tool.call        name=get_weather  params={'city': '深圳'}  result_length=23  latency_ms=0.0
fc.tool_call     tool=get_weather  arguments={'city': '深圳'}  result_length=23  latency_ms=0.3
fc.llm_call      call=2  messages=3  prompt_tokens=556
fc.final_answer  content='深圳当前天气情况如下：- 天气：雷阵雨 ⛈️ - 气温：31 摄氏度 - 湿度：80%...'
```

**四步全在日志里可见**——这就是"讲清这条链路"的证据。

**面试官会追问什么**

- 追问 1："schemas 是每次请求都重新生成吗？" 答：**不是，装饰时就生成好了**。`decorator.py:138` 的 `build_parameters(fn)` 在 import 时跑一次，结果存在 `FunctionTool._schema` 里（`decorator.py:108`）。运行时的 `run()` 只是读它。**所以工具调用路径上没有"重新算 schema"的开销**——这是设计时特意做的。
- 追问 2："如果注册器里没找到工具，你的循环会怎样？" 答：抛 `UnknownToolError`，被 `demo_fc.py:60` 的 `except AfgError` 接住，**包装成错误消息回填**，模型下一轮看到并纠正（见 Q4 的真实回答）。**整个流程不会崩、不会静默跳过**。
- 追问 3（延伸到 D6）："这个链路怎么变成真正的 Agent 循环？" 答：**把 `demo_fc.py:36` 到结尾那一整段包进 `while` 即可**——判断条件是"这轮有没有 tool_calls"，有就继续、没有就结束。要加的是熔断（连续 3 次相同 `(tool, arguments)` 强制退出），因为模型可能卡在重复调用里。

## 今日真实体验记录（附：跑真实验收）

**验收命令**：`python -m afg.demo_registry` 和 `python -m afg.demo_fc "<问题>"`（真实 API）

**5 个场景全部实测通过**

| 场景 | 提问 | 结果 |
|---|---|---|
| 正确选工具（天气） | 深圳天气怎么样 | `tool=get_weather`，参数 `{'city': '深圳'}`，最终答出带 emoji 的天气卡片 |
| 正确选工具（时间） | 现在几点了 | `tool=get_current_time`，**参数 `{}`**（无参数工具也对） |
| **幻觉防范（名字）** | 用 delete_file 删掉 a.txt | 注册器抛 `UnknownToolError` → 包装回填 → **模型如实说"我没有这个工具"并列出真实能力清单** |
| **幻觉防范（该不该调）** | 帮我删除项目里那个没用的文件 | **`fc.no_tool_call`** —— 模型没乱调工具，直接说明自己没有文件系统能力 |
| schema 质量 | — | 自动生成的 schema 与 D4 手写版**逐字段一致**，无退化 |

**发现 1：修掉了 D4 遗留的真 bug**

D4 的 `builtin.py:70` 是 `expr = kwargs["expr"]`，模型**没给** `expr` 时抛 `KeyError`——而 D4 的调用方只 `except ToolError`，**抓不住，程序直接崩**。D4 没暴露纯粹是因为模型每次都乖乖给了参数。

D5 把校验提到 `FunctionTool.run()`（`decorator.py:113-119`），三类问题全拦，且**对所有 `@tool` 工具自动生效**。提示词层面的意义：错误变成"参数错误：缺少 expr"回填给模型 → **模型自己改参数重试**，而不是程序崩掉。

**发现 2：描述质量的一次小退化，被 schema 对照抓出来**

自动生成描述时，我把多行 docstring 用 `" ".join()` 拼接，中文结果变成 `"...和括号。 只能算纯数字..."`——**句号后多了一个空格**。而且 D4 版里"例如 37*89 或 (1+2)*3"这个例子丢了。

改成 `"\n".join()` + 把例子补回 docstring 后：
```
'计算一个数学表达式的值。支持加减乘除、取余、乘方和括号，例如 37*89 或 (1+2)*3。\n只能算纯数字，表达式里不能出现变量名或函数调用。'
```

**这件事本身值得记**：`demo_registry.py` 存在的意义就是"把 schema 打出来人工看"——**不看就发现不了**。这也说明"D5 的 schema 自动生成是有代价的：机制对了，文案质量还得人盯"。

**发现 3：装饰器让日志从"调用点"移到了"工具身上"**

对比 D4 和 D5 的同一段日志：

```
D4：fc.tool_call  tool=get_weather ...            ← 只有 demo 这一个调用点有日志
D5：tool.call     name=get_weather ...            ← 工具自己打，谁调都有
    fc.tool_call  tool=get_weather ...            ← 调用方视角仍然保留
```

**两层视角各有用处**：`tool.call` 答"工具自身耗时"，`fc.tool_call` 答"从发起到拿到结果"（含注册器查找）。等 D6 的 Agent 循环上来，会有很多调用点，**那时"日志长在工具身上"的价值才真正体现**。

**发现 4：代码量对比**

| | D4 手写 | D5 声明式 |
|---|---|---|
| `builtin.py` | 128 行 | 91 行 |
| 工具定义方式 | 类 + `parameters()` 方法 + `run()` 方法 | `@tool` + 函数 + docstring |
| schema 位置 | 手写（可能和实现漂移） | 自动生成（单一真源） |

**成本记录**：D5 验证共约 8 次真实调用（demo_registry 1 次 + demo_fc 3 个场景各 2 次 + 重跑）。
