## Q1：为什么 LLM 需要外置记忆模块？

**是什么**

三句话：上下文是**易失的**（进程结束就丢）；窗口是**有限的**（超了要截断，D2/D3 已经在处理）；而任务是**跨会话、持续多轮**的。LLM 自己没有持久状态，所以 Memory 模块的本质是——**替语言模型补上状态管理能力**。

**我的实现（D8 里可见的证据）**

`SQLiteMemory` 把对话写进一个 **SQLite 文件**（`memory-dev.db`），进程退出文件还在：

- 建库：`memory/sqlite.py:11` 的 `sqlite3.connect(db_path)` + `:14-21` 的建表语句
- 落库：`agents/core.py:88`（正常结束）和 `:138`（熔断结束）两处调 `_remember` → `memory/sqlite.py:33` 的 `executemany` 插入

**真实证据**：跨两次进程启动，第二次开局就答出名字——

```
（第一次）memory.load count=0 → memory.save count=2 → 答"好的，小明，我记住了"
（第二次）memory.load count=2 → messages=4  → 答"你叫小明"
```

**面试官会追问什么**

- 追问 1："不用数据库，写 JSON 文件行不行？" 答：**能跑通，但很快会遇到三个问题**——并发写没有事务保证、查询要全量读进内存再筛、没有索引。SQLite 是"零部署成本拿到事务+索引"的最省事选择，单机场景足够。
- 追问 2："为什么不用 Redis/向量库？" 答：**按需要选**。本项目要的是"按时间取最近 k 条"，SQL 一句话的事；向量库解决的是"按语义检索"，那是 D9 检索工具和 D14 演练要覆盖的场景，不是今天。

**参考来源**

- 知乎《字节面试题：Agent 的记忆系统怎么设计》
- CSDN《面试官问：Agent 的记忆模块是怎么实现的》

## Q2：短期记忆和长期记忆的本质区别？

**是什么**

**不是按时间长短分，而是按"是否跨会话"分**：

- 短期记忆 = 当前会话的消息列表（user / assistant / tool），直接参与推理、受 maxToken 限制，靠 D2/D3 的上下文工程管理
- 长期记忆 = 跨会话持久化的知识，需要外部存储 + 检索 + 更新

一句话判断："换个进程还记不记得"——记得的才是长期记忆。

**我的实现（D8 里可见的证据）**

- 短期记忆：`agents/core.py:58-66` 的 `messages` 列表，进程结束即消失
- 长期记忆：`SQLiteMemory`，`session_id` 字段把长期记忆**按会话分组**（`memory/sqlite.py:15-21` 的表结构里就有它），`load_context` 只取当前 session 的（`:42-45` 的 WHERE 条件）

**面试官会追问什么**

- 追问 1："那你们 `session_id` 换来换去，算长期还是短期？" 答：**存储是长期的，可见范围是会话级的**。今天只做了"同一 session 的滚动对话"；要跨 session 共享事实（比如用户偏好），得再加 user_id 维度和去重逻辑——W2 之后的演进方向。

**参考来源**

- 腾讯云《Agent 记忆系统技术深度》

## Q3：记忆模块在主循环里的位置和完整闭环？

**是什么**

标准闭环：`Input → Retrieve Memory → Combine Context → LLM Reasoning → Output → Update Memory`——**推理前检索注入，推理后写回**，形成 Retrieve → Reason → Update 的循环。

**我的实现（D8 里可见的证据）**

两个钩子分别落在 `AgentCore.run()` 的头和尾：

- 推理前：`agents/core.py:59-62`——挂了记忆就先 `load_context(k=memory_load_k)`，把历史 append 到 system 之后、本次任务之前
- 推理后：`agents/core.py:88` / `:138`——两个返回点前各调一次 `_remember(messages, start)`

**关键设计**：`start = len(messages)`（`:63`）记下"历史注入完、任务还没加"的位置，`_remember`（`:199-205`）只把 `start` 之后的消息存库。没有这个游标，第二次启动时读出来的历史会被原样再存一遍，**库里每跑一次翻一倍**。

**面试官会追问什么**

- 追问 1："如果 Retrieve 回来的内容把上下文撑爆了怎么办？" 答：今天用 `memory_load_k=5`（`config.py:31`）限制条数；真要放更多，就应该走 D3 的压缩器或按重要性筛选——**记忆的写入和读回都得有配额意识**。

**参考来源**

- 阿里云《Agent 记忆系统技术深度》

## Q4：长期记忆的 Record 和 Retrieve 两个流程各自做什么？

**是什么**

- **Record（写）**：从会话消息里挑出值得记的内容 → 存储（+ 审计）。生产级还会做 LLM 抽取、区分事实/推断、向量化
- **Retrieve（读）**：按 query 取回相关内容 → 注入上下文。生产级是语义检索 Top-K + 重排

**我的实现（D8 里可见的证据）**

今天是最小实现：**全量按时间取**，没有 query 语义。

- Record：`memory/sqlite.py:24-39` 的 `save()`——只过滤掉不该存的（tool 消息、空内容），其余全部落库
- Retrieve：`memory/sqlite.py:41-53` 的 `load_context()`——`ORDER BY id DESC LIMIT ?` 取最近 k 条再翻转成正序

`BaseMemory` 签名里保留了 `query=None` 参数（`memory/base.py:6`），但 D8 不实现它——**接口先占位、实现分阶段**，这是主文档定的规矩。

**面试官会追问什么**

- 追问 1："为什么不做抽取，而是原样存？" 答：**先跑通存取再谈智能**。抽取要用 LLM（多一次调用、多一份钱），而且没有评测就不知道抽得好不好——D20 的 eval 体系建起来之前，做抽取是盲调。
- 追问 2："`ORDER BY id DESC LIMIT` 为什么不用时间戳排序？" 答：**同一秒写入的多条消息时间戳相同**（`save` 里的 `now` 是一次性取的），按时间排会不稳定；`id` 是自增主键，天然单调且唯一。时间戳留着做审计和后续的遗忘策略。

**参考来源**

- 知乎《字节面试题：Agent 的记忆系统怎么设计》

## Q5：记忆条目该存什么元数据？

**是什么**

生产级至少要：`source`（来源）、`timestamp`（时间）、`session_id`（会话）、`importance`（重要度）、`user_id`——支撑**过滤、更新、遗忘、审计**四件事。

**我的实现（D8 里可见的证据）**

今天表里五列（`memory/sqlite.py:14-21`）：`id`（主键，同时充当排序游标）、`session_id`（过滤维度）、`role`（区分 user/assistant）、`content`（正文）、`created_at`（审计用）。

**缺什么**：没有 `importance`（没法按重要度淘汰）、没有 `user_id`（没法跨会话共享）。**这两个字段是"知道该有但今天不做"**，留给后续。

**面试官会追问什么**

- 追问 1："为什么把 `role` 存下来？重建消息时不能猜吗？" 答：不能。`Message` 的 role 决定模型怎么理解这段话——历史里 user 的话和 assistant 的话混在一起就是噪声。而且 D1 的校验要求 role 合法，存错会在 `load_context` 的 `Message(...)` 处当场炸掉。

**参考来源**

- CSDN《面试官问：Agent 的记忆模块是怎么实现的》

## Q6：记忆怎么更新与遗忘？

**是什么**

- **更新**：按唯一 id 先删后插（新事实覆盖旧事实），避免矛盾记忆并存
- **遗忘**：按时间戳/重要度淘汰、过期标记，防止"垃圾堆"

**我的实现（D8 里可见的证据）**

今天**只实现了"追加"**：`save()` 只做 INSERT（`memory/sqlite.py:33-38`），没有任何 UPDATE / DELETE。已知的缺口有三个：① 同一事实说两遍会存两条；② 旧偏好不会失效；③ 库会无限增长。

**为什么可以接受**：今天验证的是"跨进程能记住"这个闭环；更新/遗忘需要**判断哪条是新的**（要么 LLM 抽取，要么结构化字段），属于 D14 之后的事。

**面试官会追问什么**

- 追问 1："那你说说遗忘策略怎么设计？" 答：三档——**容量档**（超过 N 条淘汰最旧）、**时间档**（TTL 过期）、**重要度档**（保留高重要度）。工程上通常组合：重要度低的走 TTL，重要度高的常驻。

**参考来源**

- 腾讯云《Agent 记忆系统技术深度》

## Q7：长期记忆和 RAG 有什么区别？

**是什么**

**技术同构、用途不同**：两者都是"存储 → 检索 → 注入上下文"；但 RAG 面向**静态知识库**（文档，读多写少），记忆面向**动态历史**（用户/会话，持续写入、可更新可遗忘）。

**我的实现（D8 里可见的证据）**

今天这份 `SQLiteMemory` 是"记忆"侧的：数据来源是**运行时产生的对话**（`core.py:88` 的 `_remember`），不是预置文档；而且它跟着会话走（`session_id` 过滤）。

反过来说，D9 要写的 `search_notes` 是"RAG"侧的：数据来源是**我自己的笔记文件**（静态语料），以工具的形式暴露给模型。**两条线共用同一套"存—检索—注入"骨架，但触发方式不同**：记忆是内核自动的，RAG 是模型主动调工具。

**面试官会追问什么**

- 追问 1："能用同一张表实现两者吗？" 答：能。加一个 `kind` 字段区分（conversation / document）即可——但**不建议硬合**，因为两者的生命周期、更新频率、权限模型都不一样。

**参考来源**

- 腾讯云《160+ 真题》记忆与 RAG 对比题

## Q8：生产级长期记忆组件有哪些？

**是什么**

Mem0、Zep、Memos、ReMe 等。核心构成都是五件套：**LLM 抽取 + Embedder + VectorStore + Reranker + 审计存储**——知道组件构成比背名字重要。

**我的实现（D8 里可见的证据）**

我的最小版只对应其中两件：**存储（SQLite）+ 读取（最近 k 条）**。缺的三件——抽取、向量化、重排——分别是 D9（检索）、D14（记忆升级）和后续的事。

**面试官会追问什么**

- 追问 1："那你这算什么？" 答：算**骨架验证**。五件套里最容易出问题的是"读写时机"和"去重"，这两件事在最小版里已经暴露了（今天的 `start` 游标就是去重问题）；后面每加一件，接口都不用改——因为 `BaseMemory` 是抽象协议。

## Q9：写入记忆时要注意什么？

**是什么**

四条：区分事实与推断；带时间戳与来源；可更新可撤销；**控制写入量**——不是什么都记，低价值信息是噪声。

**我的实现（D8 里可见的证据）**

今天做的是最后一条的最小版——**过滤**：`memory/sqlite.py:27-32` 跳过 tool 消息和空内容。为什么跳过 tool？因为 tool 消息没有 `tool_call_id`，重建 `Message` 会被 D1 的跨字段校验拦下（`context/messages.py:20-24`）——**存进去的每一条，将来都必须是能重建的**。

"控制写入量"的另一半——**去重**——靠 `core.py:63` 的 `start` 游标：只写本轮新增。

**面试官会追问什么**

- 追问 1："只过滤两类，量还是很大怎么办？" 答：加两条闸——写入前按长度/关键词筛（比如纯寒暄不记），或写入后按重要度定期淘汰（Q6）。今天的 `memory_load_k` 只管读侧，**写侧配额**是下一个要补的口子。

## Q10：会话记忆的滑动窗口/摘要各有什么问题？

**是什么**

- **滑动窗口**：只保留最近 N 条——实现简单，但会**丢掉早期的关键信息**（"我叫小明"在第 1 句，窗口滑过去就没了）
- **摘要**：把旧内容压成一段——省 token，但**丢失细节**、生成有成本、且摘要本身可能失真
- 工程结论：混合使用——**关键事实外置到长期记忆，窗口内保留近期完整历史**

**我的实现（D8 里可见的证据）**

今天走的是"混合"里的前半段：**关键事实（全部 user/assistant 对话）落在 SQLite，进程重启后取回最近 k 条**（`sqlite.py:41-53` + `core.py:59-62`）。

**今天亲手摸到的两个边界**：

1. `memory_load_k=5` 就是"窗口大小"——设小了老事实照样丢（和滑动窗口一个毛病），设大了浪费上下文；
2. 真正的解法是"**按需检索**"而不是"按时间取"——这正是 D14 要做的 `SummaryMemory` 和后续检索要解决的问题。

**面试官会追问什么**

- 追问 1："摘要记忆怎么触发？" 答：会话结束或达到条数阈值时触发；摘要**作为一条 system 消息**替换掉被压缩的原文（D3 的压缩器已经在用这个套路）。

- waylandz《AI Agent 开发实战》第 7 章
- 本项目 D3 压缩器实现（`context/compressor.py`）
